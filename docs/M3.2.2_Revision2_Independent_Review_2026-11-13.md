## Additional P1: Pre-existing orphan lock with missing metadata sidecar

**Location:** `tools/recovery/m321_step_journal.py`, `JournalFileLock._open_fixed_lock_byte()`, `_read_metadata()`, and `acquire()`.

**Observation:** `_open_fixed_lock_byte()` opens either a newly created (`x+b`) or pre-existing (`r+b`) lock file. `_read_metadata()` returns `None` when the sidecar is absent. `acquire()` refuses a previous state other than `released` only when metadata is present. The code therefore accepts an **already-existing** fixed-byte lock file with no metadata sidecar.

**Offline reproduction:** Within a temporary local directory, precreate `review.json.lock` as a single NUL byte, do not create `review.json.lock.meta`, then call `JournalFileLock(...).acquire()`. Result: **acquisition succeeded**. No infrastructure or SQL was used.

**Why this matters:** The absence of metadata might represent a crash between lock creation and sidecar persistence or evidence tampering. It is ambiguous; the review contract says ambiguous lock ownership must fail closed.

**Recommended fix:** Track whether `x+b` actually created the file in this acquisition. If opening an *existing* lock file (`r+b`) and the metadata sidecar is missing, raise `JournalViolation`; do not synthesize a released prior state. Add an offline regression for this case. Also consider verifying the previous released sidecar's rehearsal/path identity according to policy.
