### C-02 — Qdrant physical readiness
1. Verify `PHYSICALLY_VERIFIED` requires a scoped read-after-write check of the exact point ID, document/chunk/generation, tenant metadata, expected vector parameters and committed provenance/hashes; write acknowledgement alone is insufficient.
2. Specify actual Qdrant version and read/write consistency (including replicas/resharding) before calling a point verified. A point-in-time read does **not** prove permanent durability or continued visibility.
3. Keep `STAGED_READY` and activation denied when any point is missing/mismatched, any receipt is inconsistent, or Qdrant state is unavailable; maintain stale/purge/rebuild evidence without broadening authorization.
4. Verify that a point disappearing *after* activation yields degraded availability/fail-closed retrieval and controlled recovery; MySQL post-hit/final-disclosure checks remain authoritative.
5. Require negative tests for missing vectors, mismatched payload/digest, replica lag, revoke-between-write-and-verify, stale worker replay, and crash-before/after receipt persistence.
