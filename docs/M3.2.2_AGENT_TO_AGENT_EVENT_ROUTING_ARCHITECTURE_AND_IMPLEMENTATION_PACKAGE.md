# Healthcare AI Desk — M3.2.2 Agent-to-Agent Event Routing

**Status:** Architecture and implementation package — planning only.  
**Worker status:** Disabled.  
**Execution authorization:** Not granted.  
**Production readiness:** Not certified.

## Purpose

M3.2.2 defines how a durable M3.2.1 protocol message is routed from MySQL's authoritative workflow state to an eligible internal agent consumer. It builds on the existing transactional outbox and Redis Streams delivery accelerator. It does not create a new approval authority, allow agents to invoke one another directly, or permit external LLM egress.

M2.5 remains the only policy and human-approval authority. A routed `task_assigned` message is a notification of a durable, policy-governed workflow state; it is not authorization to run an agent or a tool.

## Start gate

M3.2.2 implementation may not start long-lived routing workers until all of the following are separately accepted:

1. M3.2.1 migration, shared sequence allocator, authorization, atomicity, and tenant-isolation evidence are accepted for the intended local environment.
2. The M3.2.1 Phase A.2 review package has passed its six live gates, including the separately authorized disposable recovery rehearsal.
3. The current Alembic head, schema compatibility, outbox contract, and M2.5 runtime APIs are verified immediately before implementation.
4. An approved local worker lifecycle/runbook exists, including singleton/lease behavior, graceful shutdown, and crash recovery.

Until then, this document is an implementation blueprint only. It does not authorize Docker, MySQL, Redis, Alembic, recovery SQL, writer cutover, or worker activation.

## Non-negotiable invariants

- MySQL is authoritative; Redis Streams is an at-least-once delivery accelerator only.
- A consumer performs a durable MySQL deduplication check and side effect in one transaction before `XACK`.
- Every query and message is scoped by organization, project, conversation, task/execution, and assigned agent as applicable.
- A consumer revalidates recipient eligibility at consumption time; historic delivery does not preserve authority after an assignment, agent version, membership, or project status changes.
- Protocol payloads, outbox events, Redis fields, and audit records use safe routing metadata only. They contain no raw patient data, credentials, provider exception text, hidden reasoning, or plaintext encrypted content.
- `approval_requested` and `approval_decided` are notifications of a pre-existing M2.5 record. They never change approval or runnable execution state.
- Retries, replay, parallel delivery, delegation, fallback, or consumer recovery cannot bypass M2.5 PII checks or human approval.

## Routing contract

**Revision 1 conformance:** This section is normative and supersedes no later section; the entire document uses one trusted-router topology, `logical_handler_id` ledger identity, MySQL workflow transition ordering, and Runtime-owned external effects. The Revision 1 section records rationale and acceptance additions, not an alternate implementation.

### Accepted input

The only routable input is a committed, server-authored `conversation_protocol_messages` record linked to a committed `workflow_outbox_events` event. The outbox payload contains only:

```json
{
  "event_id": "uuid",
  "event_type": "conversation.protocol_message.created.v1",
  "protocol_message_id": "uuid",
  "organization_id": "uuid",
  "conversation_id": "uuid",
  "correlation_id": "uuid",
  "recipient_type": "agent|supervisor|conversation",
  "recipient_agent_profile_id": "uuid|null",
  "idempotency_key": "safe-key"
}
```

Consumers fetch the durable protocol record by its scoped ID and do not treat Redis fields as authoritative business data.

### Routing destinations

| Recipient | Route | Required checks |
| --- | --- | --- |
| `agent` | Single trusted protocol-router group creates a durable local route/execution intent for the resolved agent | Same organization/conversation/project, active profile, published version, current assignment, matching task/execution, recipient identity |
| `supervisor` | Same trusted router creates a durable coordinator intent | Server-owned supervisor identity, same scoped workflow, valid workflow version/transition/dependency state |
| `conversation` | Same trusted router creates a read/projection intent only | Active conversation scope; no implicit authorization to execute work |

The only routing stream is `had:{environment}:protocol-routing:v1`, consumed and acknowledged only by `m322-protocol-router-v1`. It contains no tenant, patient, user, project, conversation, agent, or payload data in its name. No external client or agent selects a stream/group. An inactive, unpublished, unassigned, cross-tenant, or otherwise ineligible recipient receives a durable scoped rejection/dead-letter decision before `XACK`; it is never rerouted to another tenant or agent.

## Delivery lifecycle

```text
MySQL transaction
  protocol message + audit + workflow_outbox_event commit atomically
       ↓
outbox publisher leases event
       ↓
Redis XADD (safe identifiers/routing metadata only)
       ↓
consumer XREADGROUP
       ↓
scoped durable-message lookup + eligibility/M2.5 revalidation
       ↓
MySQL transaction: logical-handler ledger + route decision + local execution/projection intent
       ↓ commit
Redis XACK
```

The publisher uses the existing M3.1.2 lease, retry, error-sanitization, and recovery contract. The routing consumer must not implement an alternate publisher or write directly to Redis as a source of truth.

### Ordering policy

`conversation_protocol_messages.sequence_number` is the server-owned shared **display** timeline order. It is not an actionable dependency watermark. State-changing routing uses the scoped MySQL `(organization_id, conversation_id, workflow_version, transition_key)` record maintained by the authoritative Supervisor/Workflow Coordinator. A route applies only its expected current workflow version; optimistic conflict reloads/defer the route and never executes it out of order.

Mixed human/protocol timeline gaps do not block routing. Duplicates map to the same transition key. Cancelled, rejected, or expired dependencies create durable non-runnable terminal/deferred outcomes. Read-only progress projections may be delivered in parallel only when they cannot advance task, execution, approval, or workflow version state.

Redis stream IDs are delivery identifiers, not timeline ordering authority.

### Idempotency and acknowledgement

1. On delivery, lock or insert the ledger key `(organization_id, workflow_outbox_event_id, logical_handler_id)` inside the consumer transaction. `logical_handler_id` is stable/versioned across restarts and replicas (initially `m322.protocol-route.v1`); `redis_consumer_id` is unique per process and observational only.
2. A duplicate ledger conflict is an expected duplicate only for the ledger's named unique key; other integrity failures are raised for monitoring/retry.
3. Commit the ledger and the allowed local side effect together.
4. Call `XACK` only after that commit. If `XACK` fails, reclaim/replay is expected and the ledger suppresses a duplicate side effect.
5. `XAUTOCLAIM` reclaims only the trusted router group's due idle pending entries. Reclaim respects the durable MySQL retry schedule/backoff and dead-letter thresholds so it cannot hot-loop an event before its next attempt time.

Delivery is explicitly **at least once**, never exactly once.

## Safety and approval boundary

The routing consumer never calls a provider, tool, HTTP endpoint, or other irreversible external system. It may create only a local, durable execution intent. Before that intent becomes runnable, the existing Supervisor/Runtime path performs the normal M2.5 policy evaluation. For high-impact work it creates/reads the authoritative pending approval and retains `waiting_approval` until an authorized human decision is durably stored.

At the final provider/tool boundary, M2.5 repeats PII-egress and approval validation against the actual final prompt/tool request. Routing may not cache, replay, or infer an approval grant. The Supervisor and any agent lack an approval API that can substitute for an authorized human.

## Worker lifecycle design requirements

The first implementation must define, test, and document:

- One bounded dispatcher/consumer process per configured worker instance; no import-time background task creation.
- Startup readiness only after dependency checks and consumer-group initialization are complete.
- Shutdown stops new claims, completes/rolls back the current MySQL transaction, and leaves unacknowledged Redis entries reclaimable.
- Publisher leases must expire safely; a former lease holder must fail fencing/ownership checks before publish.
- `redis_consumer_id` is stable for a process lifetime and unique per concurrently running worker; it is never the MySQL ledger identity. `logical_handler_id` is stable/versioned across replicas.
- Health/readiness reports backlog, oldest pending age, lease/reclaim failures, safe error codes, and no sensitive payloads.

## Failure handling and audit

| Failure | Required behavior |
| --- | --- |
| Redis unavailable before publication | Keep MySQL outbox event pending/retryable; do not lose or synthesize delivery |
| Publisher crashes after `XADD` | At-least-once replay is acceptable; consumer ledger suppresses duplicate side effect |
| Consumer crashes before commit | No ledger/side effect commit; pending stream entry is reclaimable |
| Consumer crashes after commit before `XACK` | Reclaim and ledger-based dedup; side effect remains once |
| Recipient becomes ineligible | Commit durable scoped `rejected` decision and coordinator-notification intent before `XACK`; do not execute |
| M2.5 denial or pending approval | Do not invoke runtime/provider/tool; preserve `waiting_approval`/denial state |
| Unexpected integrity error | Roll back and raise; never classify it as a duplicate without named-constraint verification |

Audit records include correlation/event/message IDs, actor/consumer identity, safe status/reason code, attempt/lease information, and timestamps. They exclude patient content, prompts, credentials, and raw provider errors.

## API and compatibility boundary

M3.2.2 adds no public client endpoint and does not alter existing conversation APIs. It consumes the additive M3.2.1 contract internally. M3.2.4 later owns group-chat read projections and APIs; M3.2.3 owns task-dependency coordination.

No historical Alembic migration is edited. A new migration is not presumed: any schema addition must be justified by implementation evidence and be forward-only from the actual current head.

## Implementation workstreams

1. **Routing adapter:** Map an eligible, persisted protocol-message event to a bounded internal route without adding execution authority.
2. **Consumer service:** Fetch, scope, revalidate, ledger-deduplicate, and acknowledge only after commit.
3. **Lifecycle integration:** Explicit startup/shutdown, consumer groups, lease ownership, reclaim, metrics, and safe operator replay.
4. **Safety bridge:** Call existing Supervisor/Runtime/M2.5 services rather than duplicating their approval or PII policy.
5. **Audit/observability:** Correlation-safe logs, metrics, backlog health, and repair/replay audit trail.

## Revision 1 — P0 routing-blocker resolutions

**Review response:** These are normative design decisions that resolve the five P0 architecture blockers from the independent review. They are not implementation, test, migration, worker, or execution evidence.

### R1-P0-01 — Stable logical-handler deduplication identity

The MySQL consumption ledger identity is:

```text
(organization_id, workflow_outbox_event_id, logical_handler_id)
```

`logical_handler_id` is a stable, versioned handler role such as `m322.protocol-route.v1`; it is identical across worker restarts and replicas until an explicitly reviewed handler-semantics migration. It is never a process, pod, hostname, or Redis consumer identity.

`redis_consumer_id` is unique per live worker process and is used only for Redis observability/pending-entry ownership. It is not stored in, or used to select, the deduplication key. The M3.1.2 ledger schema/API must be verified or extended forward-only before implementation so it can enforce this exact unique identity.

After a MySQL commit followed by failed `XACK`, a different `redis_consumer_id` reclaiming the same event must find the same logical-handler ledger record and produce no second local effect or external intent.

### R1-P0-02 — One authoritative routing topology

M3.2.2 selects one topology: a single trusted **protocol router** consumer group per environment, not recipient-specific consumers in a shared group and not publisher fanout.

```text
workflow outbox → Redis stream had:{environment}:protocol-routing:v1
                 → group m322-protocol-router-v1
                 → trusted router: scoped MySQL lookup/revalidation
                 → durable local route-intent / rejection decision
```

The stream name contains no organization, patient, user, project, conversation, agent, or payload data. The router is the only consumer group permitted to acknowledge this stream. It resolves the recipient from MySQL after consuming; agents never subscribe to this stream and never choose a Redis stream/group.

Wrong-recipient, missing-recipient, or stale-recipient delivery creates a durable scoped rejection decision before `XACK`; it is not filtered and acknowledged by an arbitrary agent. Backpressure is enforced at the router with a bounded batch size, bounded concurrent transactions, pending-age alerts, and no unbounded in-memory queue.

### R1-P0-03 — Workflow watermark, not timeline sequence, governs action

Timeline sequence remains an immutable display order only. M3.2.2 state-changing routes use a server-owned MySQL workflow transition record with this scoped identity:

```text
(organization_id, conversation_id, workflow_version, transition_key)
```

`workflow_version` is incremented only by the authoritative Supervisor/Workflow Coordinator transaction. `transition_key` is derived from the durable task/execution/dependency transition, not a Redis ID or timeline sequence. A route must read the current workflow/task/execution state and dependency outcome under its MySQL transaction, then apply only the expected version transition. Optimistic-version conflict means reload/defer; it never means execute out of order.

Mixed human/protocol timeline gaps are ignored for actionability. Duplicate messages map to the same transition key. Cancelled/rejected/expired dependencies create durable non-runnable terminal/deferred workflow outcomes. A later protocol event cannot overtake an unresolved state-changing predecessor merely because its display sequence is greater.

### R1-P0-04 — Routing creates local intent only; Runtime owns external effects

The routing consumer may atomically commit only local MySQL state: ledger row, scoped route decision, audit record, and—when eligible—a durable `execution_intent` addressed to the established Agent Runtime. It does not call an LLM, tool, HTTP endpoint, notification provider, or any irreversible external system.

The Agent Runtime consumes an execution intent with a separate stable idempotency key and, immediately before an external action, re-reads the current execution/approval state and calls the existing M2.5 final PII/approval gate. Rejected, expired, revoked, reassigned, or stale approval blocks the action and records a safe local outcome. The runtime owns any provider/tool idempotency contract; routing cannot infer that an earlier route decision remains valid.

### R1-P0-05 — Durable terminal reject/dead-letter decision before acknowledgement

Each consumed event has one durable MySQL routing outcome before `XACK`:

| Class | Examples | Durable outcome | `XACK` rule |
| --- | --- | --- | --- |
| Applied | Eligible route creates local execution intent | `applied` ledger/route decision | After one transaction commits |
| Transient | Redis/database timeout, lock conflict, temporary dependency lag | Retry schedule with bounded attempt counter/backoff | No `XACK` until a later applied/terminal result |
| Permanent | Cross-tenant claim, stale/unassigned recipient, invalid envelope/version, policy denial | `rejected` terminal routing decision with safe reason code | Only after terminal decision and coordinator-notification intent commit |
| Poison/exhausted | Repeated retryable handler failure exceeds policy | `dead_lettered` terminal decision with safe reason code and last safe error code | Only after dead-letter and coordinator-notification intent commit |

Initial local defaults, subject to disposable integration evidence, are: maximum 5 attempts, exponential retry from 5 seconds capped at 5 minutes with jitter, `XAUTOCLAIM` idle threshold 60 seconds, router batch size 20, and max 4 concurrent transactions. Operators may request a scoped replay only through an audited, authorized action that creates a new replay intent; it preserves the original routing outcome, logical handler ID, correlation/causation, M2.5 enforcement, and PII controls. Direct Redis replay, acknowledgement deletion, and cross-scope replay are prohibited.

### Revision 1 acceptance additions

The R-01 through R-10 scenarios in the independent review are mandatory M3.2.2 acceptance tests. In particular, tests must use independent MySQL sessions and distinct Redis consumer IDs to prove stable logical-handler deduplication, exclusive trusted-router acknowledgement, action ordering by workflow version rather than timeline sequence, runtime-only external intents, and durable terminal poison decisions.
