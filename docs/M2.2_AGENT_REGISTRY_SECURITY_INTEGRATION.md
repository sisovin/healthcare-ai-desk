# M2.2 — Agent Registry Security Integration

## Objective
Wire Agent Registry APIs into the existing M1.3 security stack with strict organization isolation and permission guards.

## Required integrations
- Reuse `get_organization_context` and `get_access_context`.
- Enforce `require_permission` at endpoint boundary.
- Enforce organization scope consistency on every query and mutation.

## Security controls
1. Header guard:
   - reject missing `X-Organization-Id`
   - reject malformed org id
2. Token guard:
   - reject invalid/missing bearer token
   - reject token org mismatch
3. Membership guard:
   - reject users not in target organization
4. Permission guard:
   - require `agent.read` or `agent.write` per operation

## Data access invariants
- Every DB query must include `organization_id` predicate.
- No lookup by `agent_id` without org predicate.
- Slug uniqueness always resolved within org scope.

## Validation
- Endpoint tests cover 401/403/404/409 branches.
- Regression tests confirm no behavior drift in M1.3 auth/org routes.

## Implementation package status
Implemented components:
- Agent endpoints are protected by `require_permission(...)`:
  - `POST /api/v1/agents` -> `agent.write`
  - `GET /api/v1/agents` -> `agent.read`
  - `GET /api/v1/agents/{agent_id}` -> `agent.read`
  - `PATCH /api/v1/agents/{agent_id}` -> `agent.write`
- Organization-scoped data access is enforced in service queries/mutations.
- Security integration coverage is implemented in endpoint tests.

Compatibility guarantees:
- Existing API routes remain unchanged.
- Migration history remains forward-only (`...0006` stays current).
- Existing agent records are preserved; no destructive data migration is introduced in M2.2.
