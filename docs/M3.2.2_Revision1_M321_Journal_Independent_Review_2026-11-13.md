## M3.2.1 — confirmed offline journal concerns

### P0-01 — Windows lock acquisition corrupts lock metadata

`JournalFileLock.acquire()` opens the lock file with `a+b` (source lines 348–355), then `_lock_os_handle()` writes `b"\0"` on Windows before locking (lines 319–325). Append mode writes at the **end** regardless of `seek(0)`. Therefore a new lock file becomes a NUL byte and a previously released JSON lock becomes JSON followed by NUL; the ensuing `json.loads()` rejects either. An independent cross-platform append-mode simulation reproduced both invalid byte sequences, **not** an actual Windows-native run.

**Required:** Redesign the Windows lock file around an exclusive fixed lock byte and non-append-mode metadata, or use a proven cross-platform lock implementation with a separate metadata sidecar. Test real Windows acquisition, clean reacquisition, concurrent processes, crash leftovers, and invalid metadata. Do not auto-break ambiguous lock records.

### P0-02 — A failed persistence operation does not latch the session closed

`JournalMutation.pass_and_persist()` mutates `self.journal` before `write_journal()` succeeds (lines 495–499). On a simulated persistence failure, the on-disk journal remained `PREPARED` while the in-memory object had advanced to `IN_PROGRESS_REVIEW_ONLY`. Restoring the writer and calling `prepare_and_persist()` then successfully persisted the subsequent `PREPARED` step. **This violates the requirement to stop after any persistence failure and to verify each outcome before the next step.**

**Required:** Add a terminal **session-fault latch** on any mutation, write, reload, integrity, or lock failure; disallow all later actions through that mutation session. Favor building immutable candidate state, writing it successfully, and only then replacing the in-memory state. Add a failure-injection regression for each persistence stage.

### P0-03 — First persistence can batch PREPARED and PASSED

The persistence layer accepts a fresh, in-memory `PREPARED → PASSED` pair and writes the complete journal in one first write. Independent offline probe confirmed first-ever persistence as `IN_PROGRESS_REVIEW_ONLY` with both records already included. This bypasses the promised durable pre-execution PREPARED barrier.

**Required:** Enforce one journal lifecycle transition per durable write (new journal → one PREPARED; PREPARED → one outcome; completed outcome → one next PREPARED), based on the previously reloaded durable state; reject fresh multi-record submissions. An approved future runner must only proceed when the distinct PREPARED write and reload were verified.

### P1-01 — Unresolved PREPARED can be finalized by a new session without an explicit reconciliation gate

An offline probe persisted `PREPARED` in one `JournalMutation`, reopened it in a different `instance_id/run_nonce`, and successfully called `pass_and_persist()` with fabricated passing evidence. No reconciliation approval or reviewed outcome reference was required. The code executes no SQL; the risk is future evidence and runner integration.

**Required:** On `__enter__`, detect unresolved PREPARED from an earlier ownership epoch and block ordinary outcome recording until an independently authorized *reconciliation-only* process records the state. Do not automatically retry the SQL.

### P1-02 — Enter failure can leave the file lock held

If `JournalMutation.__enter__` acquires a lock but `load_journal()` raises for malformed JSON, `__enter__` exits exceptionally without releasing the lock (lines 477–483). An offline probe confirmed the lock handle remained held. A failed `__enter__` will not trigger context-manager `__exit__`.

**Required:** Wrap post-acquire operations in `try/except` with lock release on every failure, preserving the original reason and fail-closed behavior.

### Further durability conditions

A same-directory temporary file, fsync and atomic replacement are good foundations; still verify parent-directory persistence/Windows filesystem semantics where relevant. SHA-256 detects accidental corruption but is not an independent digital signature. Snapshot digests must be matched against separately captured snapshot bytes before an approved rehearsal.

## Targeted regression acceptance checklist

1. **Windows lock test:** create/reacquire lock; two independent processes contend; corrupt lock refuses; crash leftover refuses; no injected NUL/JSON corruption.
2. **Failure latch:** after any write, fsync, replace, reload, integrity, or lock failure, the same mutation session cannot prepare or finalize another step.
3. **Exactly one transition per persist:** reject first-write PREPARED+PASSED; enforce distinct persisted PREPARED outcome records; verify initial and later transitions.
4. **Restart rule:** a different run nonce cannot silently finalize an unresolved PREPARED; independent reconciliation evidence is required.
5. **Lock cleanup:** any `__enter__` failure releases the OS handle without overwriting the evidence file.
6. **Routing architecture consistency:** one canonical topology, dedup key, and action-ordering contract in both main sections and Revision 1.
7. **Live gates:** remain pending until separate disposable rehearsal approval, execution, fresh-session evidence and reference schema comparison.
