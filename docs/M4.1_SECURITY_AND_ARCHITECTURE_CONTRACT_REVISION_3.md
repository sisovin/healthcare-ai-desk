# Healthcare AI Desk — M4.1 Security & Architecture Contract, Revision 3

**Status:** Review-only design refinement; pending independent re-review.
**Execution authorization:** `false`.
**Supersedes:** Revision 2 §5.3, §6.2, §8, §9, and its final decision. All
other Revision 2 requirements remain binding.
**Safety authority:** M2.5 remains the sole authority for high-impact approval

Revision 3 resolves the two narrow design findings R2-01 and R2-02 and adds a
non-approval governance decision-register template. It does not create any
schema, Qdrant collection, index generation, provider request, worker, or
external egress capability.

## 1. R2-01 — Exact index-generation activation CAS

### 1.1 Generation model and first-generation rule

Every tenant-scoped document version uses a non-null authoritative
`active_index_generation` integer with initial value `0`. Generation `0` means
“no active vector generation.” The first index activation therefore has:

```text
expected_prior_active_index_generation = 0
requested_index_generation             = 1
```

For later activations, `requested_index_generation` must equal
`expected_prior_active_index_generation + 1`; skipped generations are denied.
The incoming event binds all of the following immutable values:

```text
organization_id, document_version_id, expected_prior_active_index_generation,
requested_index_generation, expected_revocation_generation,
collection_schema_generation, embedding_model_version,
chunk_manifest_sha256, expected_chunk_count, idempotency_key
```

Neither the worker nor Qdrant may select or infer the expected predecessor.

### 1.2 Staged-generation readiness evidence

Before activation, the worker records an authoritative generation manifest and
per-chunk receipts. A generation is `STAGED_READY` only when MySQL verifies:

1. the source version remains `APPROVED_ACTIVE` at the expected revocation
   generation;
2. the manifest SHA-256, collection-schema generation, model version, expected
   chunk count, and immutable source/redaction provenance match the event;
3. every expected chunk has exactly one receipt under the composite identity
   defined by Revision 2 §5.2, with matching deterministic point ID and
   provenance; and
4. no receipt is missing, stale, duplicated with different provenance, denied,
   or attached to another organization/document version/generation.

Qdrant points for a staged generation must include the staged generation marker
and cannot pass candidate filters until MySQL makes that exact generation
active. Qdrant physical upsert is not readiness evidence by itself.

### 1.3 Normative activation transaction

The activation service opens a short MySQL transaction, locks the authoritative
document-version and generation-manifest rows, rechecks lifecycle/revocation
and `STAGED_READY`, then performs an equality-based CAS. Its required semantic
shape is:

```text
UPDATE document_versions
SET active_index_generation = :requested_index_generation,
    index_visibility_state = 'ACTIVE'
WHERE organization_id = :organization_id
  AND id = :document_version_id
  AND lifecycle = 'APPROVED_ACTIVE'
  AND revocation_generation = :expected_revocation_generation
  AND active_index_generation = :expected_prior_active_index_generation;
```

The activation transaction additionally verifies that
`requested_index_generation = expected_prior_active_index_generation + 1` and
that the matching manifest is `STAGED_READY`. It must not replace equality with
`< requested`, infer a predecessor, skip an unready generation, or activate a
generation with incomplete receipts.

An update count other than one is a non-activating stale/mismatch disposition.
The worker records a minimal stale reason, retains or creates a scoped purge
intent for staged points, and does not acknowledge the event as active. A new
generation requires a fresh authoritative event; replay of the stale event
cannot change its expected predecessor.

### 1.4 Replay, crash, and retrieval effects

The MySQL manifest/receipt/activation outcome commits before Redis `XACK`.
Reclaimed delivery reuses idempotent receipt identity and observes the durable
CAS result. It cannot activate a different generation.

Retrieval remains protected by the Revision 2 post-search and final-disclosure
checks: it accepts only the document version’s exact active generation after
authoritative MySQL authorization. Transient staged or stale points therefore
cannot become accessible due to an old worker, replay, or delayed purge.

Required future evidence expands M4-T04/M4-T05 to include first generation,
out-of-order workers, prior-generation mismatch, skipped generation,
incomplete manifest, revoke-before-upsert, revoke-after-upsert, stale cleanup,
commit-before-XACK, and duplicate/reclaimed delivery.

## 2. R2-02 — Atomic single-use M2.5 egress decision

### 2.1 M2.5-owned attempt state

M4 requests, but does not create, approve, consume, or alter, an M2.5 egress
decision. M2.5 (or an explicitly authorized M2.5-owned service) maintains a
durable attempt record keyed by `egress_attempt_id` with an immutable binding:

```text
operation_id, operation_type, canonical_payload_sha256,
post_redaction_payload_sha256, classification_policy_version,
principal_id, organization_id, purpose_of_use, agent context,
provider, endpoint, model, region, retention/no-training terms,
destination type, decision policy version, issued_at, expires_at
```

The state machine is:

```text
NOT_SENT → RESERVED → CONSUMED
                  └→ EXPIRED | CANCELLED
CONSUMED → UNCERTAIN
```

Terminal `CONSUMED`, `UNCERTAIN`, `EXPIRED`, and `CANCELLED` states cannot
return to `NOT_SENT`. `UNCERTAIN` means the sender cannot prove that the
provider did not receive/process the request; it is not a retry permission.

### 2.2 Atomic reservation and consumption

Immediately before external transmission, the sender calls an M2.5 API that
atomically validates the complete immutable binding, verifies policy and expiry,
and changes the unique attempt from `NOT_SENT` to `RESERVED` for that sender.
Only the reservation holder may perform the one-time atomic transition to
`CONSUMED` before transmission. A concurrent, repeated, expired, changed, or
otherwise mismatched attempt is denied.

The API returns no payload authorization when the exact payload/destination
binding differs. Any change to query/chunk text, redaction result, retrieved
candidate set, provider, endpoint, model, region, retention term, operation,
or destination invalidates the request and requires a new M2.5 decision.

M4 must preserve the M2.5 attempt ID and policy decision reference in minimal
audit metadata, never raw content, credentials, patient identifiers, or a
reusable capability token.

### 2.3 Failure, timeout, and retry semantics

After `CONSUMED`, a connection reset, timeout, process crash, malformed
provider response, or unknown provider acknowledgement changes the attempt to
`UNCERTAIN` when observed. The decision is never reused. The system does not
claim exactly-once external delivery.

Any retry requires a fresh exact-payload M2.5 evaluation and a new
`egress_attempt_id`. When a provider supports idempotency, the approved sender
may supply a stable logical-operation idempotency key under the new decision;
without provider idempotency, automatic retry after `UNCERTAIN` is prohibited
and the policy/operations workflow must decide the safe next action.

An error confirmed before reservation/consumption may be represented as
`CANCELLED` only by M2.5 under its audited rules. M4 cannot reset or recycle an
attempt. Local processing remains subject to normal authorization and audit;
remote Qdrant, telemetry, backups, and support paths are external destinations
and require classification/decision handling under this contract.

Required future M4-T06 evidence includes concurrent sender races, changed
post-redaction payload, denied provider/region/model fallback, expiry, provider
timeout after consumption, retry with a fresh decision, and provider
idempotency behavior where available.

## 3. Governance decision-register requirement

The companion
[`M4.1_GOVERNANCE_DECISION_REGISTER_TEMPLATE.md`](M4.1_GOVERNANCE_DECISION_REGISTER_TEMPLATE.md)
defines the seven required decision records. A template entry, draft, or
unapproved record is not evidence of governance approval. M4.2 remains blocked
until all seven records are current, approved, version-controlled, and
independently verified against the actual environment and M2.5 interface.

## 4. Revision 3 acceptance contract

Before M4.2 schema planning can be accepted without conditions, an independent
review must confirm:

1. the equality CAS, first-generation rule, readiness manifest, and stale
   disposition are sufficient and compatible with the intended MySQL schema;
2. M2.5 can provide the owned atomic reservation/consumption API and the
   `UNCERTAIN` behavior without creating a bypass or exactly-once claim;
3. the seven governance records are actually approved—not merely templated;
4. the M4-T01 through M4-T10 implementation evidence plan includes the added
   R2-01/R2-02 negative/concurrency scenarios; and
5. M2.5 and all separately gated M3.2.1 work retain their existing authority
   and pending status.

## 5. Decision

Revision 3 is prepared for review-only independent assessment. It does not
authorize M4.2, a forward-only migration, Qdrant deployment, indexing,
ingestion, retrieval, worker activation, external egress, or any shared
environment modification.
