## Target additive schema

### 1. Conversation timeline allocator

Add to `conversations`:

```text
next_timeline_sequence INTEGER NOT NULL DEFAULT 1
CHECK (next_timeline_sequence >= 1)
```

Backfill before any protocol rows are accepted:

```sql
UPDATE conversations c
LEFT JOIN (
  SELECT organization_id, conversation_id, MAX(sequence_number) AS max_sequence
  FROM conversation_messages
  GROUP BY organization_id, conversation_id
) m ON m.organization_id = c.organization_id AND m.conversation_id = c.id
SET c.next_timeline_sequence = COALESCE(m.max_sequence, 0) + 1;
```

The exact MySQL SQL will be validated in the migration against the target MySQL version and the project’s Alembic conventions. New code must allocate by locking the scoped conversation row, reading this counter, incrementing it, and inserting the message in the same transaction.

- `UNIQUE (organization_id, id)`.
- `UNIQUE (organization_id, conversation_id, sequence_number)`.
- `UNIQUE (organization_id, conversation_id, idempotency_key)`.
- Composite FK `(organization_id, conversation_id)` → `conversations(organization_id, id)`.
- Composite FK `(organization_id, sender_agent_profile_id)` → `agent_profiles(organization_id, id)`.
- Composite FK `(organization_id, recipient_agent_profile_id)` → `agent_profiles(organization_id, id)`.
- `CHECK` sender/recipient identity forms, recipient types, protocol types, and data classification.
- Conversation timeline and recipient lookup indexes.

The physical per-table sequence unique index is a local guard only. Cross-table uniqueness is guaranteed by the server-owned counter plus conversation row lock; it cannot be delegated to two independent unique indexes.

## DDL implementation order

1. Run `alembic current` and `alembic check`; confirm the real head at that moment.
2. Generate a forward-only Alembic revision with the confirmed head as `down_revision`.
3. Rehearse all DDL and backfill against a disposable database containing representative conversation messages.
4. Enter an explicit local cutover window: reject new conversation writes and stop/disable all background writers that can create conversation messages or protocol messages.
5. Wait for in-flight conversation write transactions to drain. Verify no active application writer still holds an open conversation-write transaction before running the migration.
6. Add nullable/defaulted `next_timeline_sequence`; run the deterministic backfill while writes are quiesced; validate no NULL or value below 1; then enforce non-null/check.
7. Create `conversation_protocol_messages`, its scoped composite FKs, checks, unique constraints, and indexes.
8. Deploy the user-message writer refactor that uses the shared allocator. Protocol-message writes remain disabled until that deployment is verified.
9. Verify source/runtime configuration contains no remaining `MAX(sequence_number) + 1` conversation-message allocation path and that every enabled writer uses `next_timeline_sequence` under the conversation row lock.
10. Enable protocol-message writes, then re-enable normal conversation writes only after the migration, allocator verification, and smoke tests succeed.
11. Confirm `alembic current`, `alembic check`, schema inspection, and a post-cutover write/read smoke test.

MySQL DDL is non-transactional under the current Alembic context. The migration must therefore use additive, restart-safe steps and be tested on a copy/disposable environment before any shared local database upgrade.

### P0 cutover invariant

The backfill SQL is valid only while all writers that allocate conversation sequence numbers are quiesced. It is not safe to run the backfill concurrently with the legacy `MAX(sequence_number) + 1` writer: a write committed after the aggregate read could make `next_timeline_sequence` stale and allow a cross-table collision.

The required order is therefore:

```text
quiesce conversation/background writers
  → drain in-flight writes
  → apply additive DDL + backfill
  → deploy shared-allocator user writer
  → verify no legacy allocator remains
  → enable protocol writer
  → re-enable normal writes
```

If the cutover verification fails, normal writes remain disabled until the team has either corrected the writer deployment or executed an explicitly reviewed forward recovery procedure. The plan must not restore the legacy allocator after protocol rows have been committed, because that would violate the shared-timeline invariant.

### P0 partial-MySQL-DDL failure recovery procedure

MySQL DDL may persist even if a later migration statement fails and Alembic has not recorded the revision. **Do not automatically rerun the migration** against a partially changed schema. Keep conversation/protocol writers quiesced and follow this procedure.

1. Preserve the failure output, migration revision source, Alembic current revision, and exact database/schema identity.
2. Inspect the live schema read-only (`information_schema`/`SHOW CREATE TABLE`) to record the actual columns, defaults, nullability, checks, tables, indexes, and foreign keys. Inspect row counts and counter values without modifying application data.
3. Compare actual state with the intended step-by-step DDL plan and classify the failure. Determine a **forward recovery** action; do not edit historical migrations or delete/recreate volumes.
4. Reproduce the same partial state and proposed forward recovery on a disposable database before applying it to the shared local database.
5. Apply only the reviewed, idempotent recovery action. Reinspect the schema and data invariants, then reconcile Alembic version state only after the schema fully matches the revision’s intended end state.
6. Run migration, allocator, and full regression verification before re-enabling writers.

| Failure point | Required inspection | Permitted recovery direction |
| --- | --- | --- |
| Counter column created; backfill failed | Confirm column type/default/nullability; count NULL/invalid values; compare existing message maxima | Resume/backfill only with an explicitly reviewed, predicate-scoped forward statement after disposable rehearsal; do not rerun all DDL blindly |
| Backfill completed; `NOT NULL` or `CHECK` failed | Confirm every conversation counter is present and at least one greater than its existing maximum sequence | Correct only violating rows with reviewed forward DML, rehearse constraint addition, then add the missing constraint |
| Protocol table created; FK/index/check creation failed | Inspect table columns, constraints, indexes, and orphan/incompatible rows | Add only the missing compatible FK/index/check after verifying types/collations and referenced uniqueness; do not drop/recreate the table automatically |
| DDL partially applied; Alembic version unchanged | Compare all intended objects with `information_schema` and the revision source; record the last successful statement | Complete/recover the schema to the intended end state through a reviewed forward repair revision or manual approved recovery; stamp/update Alembic only when schema equivalence is proven |

The recovery operator must record the selected procedure, disposable-environment result, exact commands, before/after schema evidence, and post-recovery Alembic current/check output in the implementation evidence. If no safe forward recovery is available, keep writers disabled and escalate rather than attempting an automatic rerun or destructive rollback.

## Write-Quiescence & Cutover Protocol

This protocol is mandatory because the legacy user-message writer allocates with `MAX(sequence_number) + 1`, while M3.2.1 introduces the shared durable timeline counter.

1. Assign a named cutover operator and announce the local maintenance window.
2. Reject new conversation writes at the API boundary and disable every background/dispatcher/protocol writer capable of inserting conversation timeline data.
3. Inspect active database sessions/transactions and wait until in-flight conversation writes finish or are safely aborted through normal application handling.
4. Record pre-cutover Alembic head/check, writer versions/configuration, conversation-message row counts, and maximum sequence values.
5. Run only the reviewed forward migration and deterministic backfill.
6. Deploy the refactored user-message writer using `next_timeline_sequence` under `SELECT ... FOR UPDATE`.
7. Verify source/runtime configuration and targeted tests show no enabled writer uses `MAX(sequence_number) + 1`.
8. Run the post-migration allocator smoke test before enabling protocol writes.
9. Enable protocol writes, then restore general conversation writes.
10. Record post-cutover schema evidence, Alembic current/check, test results, and any exception/failure details.

If any verification fails, keep timeline writers disabled and enter the Partial-DDL Recovery Runbook. Do not re-enable the legacy allocator once protocol rows exist.

## Partial-DDL Recovery Runbook

This is the operational form of the P0 recovery procedure. MySQL DDL can persist when a later statement fails; do not rerun the original migration automatically.

1. Keep writes quiesced; preserve command output, exception details, revision source, and current Alembic state.
2. Inspect actual schema and data state read-only: columns/defaults/nullability/checks, indexes/FKs, row counts, and counter/message invariants.
3. Identify the exact last successful migration step and compare it with the intended revision end state.
4. Recreate the observed partial state in a disposable environment.
5. Design and test a narrow forward repair for that state only. Historical migration files, volumes, and unrelated data are never reset or recreated.
6. Apply the reviewed repair; rerun schema/data invariant checks.
7. Reconcile Alembic revision state only after the actual schema fully matches the intended migration end state.
8. Run allocator, security, migration, and full regression tests before reopening writers.

Escalate when a safe forward repair is not available. Destructive rollback or automatic migration rerun is prohibited.

## P1 implementation decisions — finalized for migration design

### Sequence capacity and overflow behavior

Existing `conversation_messages.sequence_number` is a signed MySQL-compatible `INTEGER`. To preserve compatibility, M3.2.1 will use the same signed `INTEGER` range for `conversations.next_timeline_sequence` and `conversation_protocol_messages.sequence_number`; it will not introduce `BIGINT` for only one half of the shared timeline.

- Maximum supported allocated sequence: `2,147,483,646`.
- Before allocation, if `next_timeline_sequence >= 2,147,483,647`, the allocator fails closed with a domain capacity error before changing the counter, inserting a message, audit row, or outbox event.
- The migration `CHECK` must constrain `next_timeline_sequence` to `>= 1` and `<= 2147483647`.
- Capacity exhaustion is an operator-visible condition; it requires an explicitly reviewed future compatibility migration, not counter reset or reuse.

### Composite FK compatibility — verified local MySQL facts

Read-only inspection of the configured local MySQL database confirmed:

| Referenced table | Referenced key | UUID columns | Collation |
| --- | --- | --- | --- |
| `conversations` | `uq_conversations_org_id (organization_id, id)` | `VARCHAR(36)` | `utf8mb4_unicode_ci` |
| `agent_profiles` | `uq_agent_profiles_org_id (organization_id, id)` | `VARCHAR(36)` | `utf8mb4_unicode_ci` |

The migration must create all protocol UUID FK columns as nullable/non-null `VARCHAR(36)` with the same `utf8mb4_unicode_ci` collation and must reference exactly those composite unique keys. It must inspect the generated DDL/SQLAlchemy dialect output before upgrade; a mismatch in length, character set, collation, or referenced index blocks implementation.

### Idempotency duplicate-key behavior

The protocol write service owns the complete transaction: counter allocation, protocol-message insert, audit row, and outbox row.

1. It locks the conversation and computes the canonical authoritative fingerprint.
2. It checks for an existing scoped idempotency key before allocating a sequence.
3. On MySQL duplicate-key failure, it rolls back the entire original session; it must never reuse that failed transaction.
4. It opens or receives a fresh session and re-reads the scoped message by idempotency key.
5. Same fingerprint returns the original durable message; a different fingerprint returns a deterministic conflict.
6. It verifies no second audit/outbox record exists before returning.

### Retention and audit preservation

- Protected protocol payloads have a default retention expiry of 90 days, configurable only through controlled server configuration.
- At expiry, the ciphertext is removed or cryptographically rendered unreadable; the redacted display is replaced by a fixed retention marker.
- `conversation_audit_logs`, `AgentExecutionAuditLog`, and outbox/consumption records retain immutable, minimal action/ID/status/timestamp evidence according to their applicable retention policy. They never retain raw protocol payloads, patient identifiers, or credentials solely to preserve auditability.

### Encryption and historical readability

- No plaintext fallback exists. Encryption or key-reference validation failure rolls back the complete write transaction.
- Writes use the active configured conversation-key reference only.
- Reads support explicitly configured historical key references until their protected payloads expire.
- Key rotation is append-only: introduce/validate the new key reference, make it active for new writes, retain authorized historical read keys, then retire a key only after all governed ciphertext is expired or re-encrypted under a separately approved operation.

### Typed payload enforcement

All nine Revision 1 message-type schemas are mandatory. Validation happens before timeline allocation. The service accepts canonical JSON objects only, rejects unknown fields, and enforces the 16 KiB redacted / 64 KiB encrypted serialized limits. The allow-list in Schema Contract Revision 1 is the initial authoritative field set; expansion requires contract review, schema/versioning consideration, and tests.
