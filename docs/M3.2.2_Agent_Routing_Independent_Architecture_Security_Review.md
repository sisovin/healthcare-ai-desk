## Executive assessment

The design correctly establishes MySQL as the authoritative state, Redis Streams as an at-least-once delivery accelerator, atomic MySQL consumer-side ledger/side effects, XACK after commit, tenant and recipient revalidation, M2.5 final policy enforcement, and privacy-safe routing metadata. These are meaningful security and reliability foundations.

Several high-impact contracts need explicit decisions, not just implementation details: (1) durable deduplication identity, (2) Redis group topology and unintended delivery, (3) ordering across a shared human/protocol timeline, (4) external side effects and M2.5 revocation/time-of-check gaps, and (5) persistent poison/dead-letter resolution. The document itself does not demonstrate that any live routing behavior passes tests.

## Blocking findings (P0: resolve before runnable routing)

### P0-01 — Durable deduplication identity must not follow the Redis worker instance

**Source:** Idempotency and acknowledgement; Worker lifecycle.

The ledger is keyed by `(organization_id, event_id, consumer_name)` while the worker identity is described as unique per concurrently running process. If `consumer_name` takes that per-process identity, reclaim/replay with another worker may create a second ledger row and repeat a side effect.

**Required contract:** Distinguish `logical_handler_id` (stable across restarts and replicas; MySQL ledger identity) from `redis_consumer_id` (unique per live worker, observational only). Validate the existing M3.1.2 ledger API semantics before reusing it.

**Evidence:** Commit an event under worker A, fail XACK, reclaim as worker B with a different Redis consumer name, and verify one MySQL ledger row and one effect in an independent MySQL session.

### P0-02 — Select a Redis routing topology that cannot lose or misdeliver a recipient's event

**Source:** Routing destinations, which offer “Agent-specific consumer group or safely filtered shared group”.

In a Redis consumer group, entries are allocated among group members, not broadcast to all members. A shared group with different recipient-specific consumers can deliver an event to the wrong consumer. Filtering alone is not safe if a wrong consumer acknowledges or repeatedly holds a record intended for another.

**Required contract:** Specify one topology explicitly:
- A trusted, scoped router consumer group performs the authoritative recipient lookup and forwards into durable scoped work; or
- Each recipient has a separately owned stream/group with audited publisher fanout and retention.

Define exact stream naming, tenancy boundaries, group ownership, wrong-recipient behavior, acknowledgement conditions, and backpressure. No direct agent selection of stream or group.

**Evidence:** Parallel consumers for different recipients, delivery/reclaim/restart, with zero wrong-recipient effects and no lost messages.

### P0-03 — Distinguish shared timeline order from actionable transition dependencies

**Source:** Ordering policy. M3.2.1 uses one timeline sequence across human and protocol messages.

Protocol message sequence numbers need not be contiguous: e.g., user message 1, protocol message 2, user message 3, protocol message 4. A coordinator waiting for protocol message 3 as a predecessor could block forever. Conversely, later message 4 must not overtake a pending state-changing predecessor.

**Required contract:** Define a scoped MySQL workflow transition/version or explicit dependency watermark, derived from authoritative state. Specify how mixed user/protocol messages, gaps, duplicates, cancelled tasks, and out-of-order delivery are treated. Timeline sequence is useful for display; it is not by itself proof of runnable dependency satisfaction.

**Evidence:** Interleaved human/protocol writes and out-of-order/replayed protocol events; preserve state transitions without deadlock or duplicate execution.

### P0-04 — Prevent external irreversible actions from escaping the MySQL idempotency boundary

**Source:** “consumption ledger + permitted local side effect” is one MySQL transaction; M2.5 applies at final provider/tool boundaries.

MySQL transactions cannot roll back an outbound provider call, sent notification, or other external irreversible effect. Replays or failures after invocation could cause duplicate or unauthorized actions even with a durable ledger.

**Required contract:** Restrict the consumer transaction to local transactional state changes and creation of durable execution intentions. Any external action must run through the established runtime and M2.5 final gate, with an independently durable idempotency key, current approval/PII validation, and revocation-aware state transition. Do not make agent routing a direct tool invocation path.

**Evidence:** Approval denied/expired/revoked during replay or reassignment; zero provider/tool invocation and no duplicate external effect on XACK failure.

### P0-05 — Make rejected/poison delivery a durable, scoped terminal decision before XACK

**Source:** Routing destinations, failure handling, XAUTOCLAIM.

“Rejected or safely dead-lettered” does not define when an ineligible recipient's event is acknowledged, how retry exhaustion is persisted, how poison events affect later events, or whether coordinator notification is itself durable.

**Required contract:** Specify retry classes (transient vs permanent), bounded backoff/max attempts, durable MySQL rejection/dead-letter state and safe reason codes, coordinator notification intent, and a rule that XACK occurs only after the terminal or applied result is committed. Operator replay needs scoped authorization, evidence, and unchanged M2.5 enforcement.

**Evidence:** Bad recipient, stale assignment, transient Redis failure, and poison payload cannot trigger side effects, drop work silently, or retry without bounds.

## Additional important findings (P1)

### P1-01 — Bind the Redis event to authoritative outbox and protocol identities

The sample event omits project/task/execution context (which may be looked up). The consumer must fetch the outbox and protocol rows together by scoped IDs and verify event type/version, organization/conversation, recipient, idempotency, correlation, and current project/task/execution relationships. Treat every field read from Redis as untrusted. Never authorize using only the outbox JSON claim.

### P1-02 — Publisher lease fencing must be analyzed across the XADD boundary

An ownership check followed by XADD is not necessarily atomic with MySQL lease expiry. Specify fencing/compare-and-set transition behavior; acknowledge that duplicate XADD can remain possible at a crash or lease race boundary. Correctness relies on downstream durable deduplication, not a claim of exactly-once Redis publishing.

### P1-03 — Explicit Redis operational security and privacy governance

Document network isolation, Redis ACLs, TLS where required, non-sensitive stream naming, metadata allow-lists, retention/trim policy, stream memory caps, pending-entry and dead-letter monitoring, credentials handling, and audit access controls. Verify `idempotency_key` is an opaque safe routing token and cannot echo patient identifiers or secrets.

### P1-04 — Readiness and resource controls need concrete thresholds

Define lease TTL, claim idle time, maximum attempts, exponential backoff and jitter, batch/concurrency limits, shutdown grace period, backlog and oldest-entry alerts, health/readiness failures, and scoped replay approval. Numeric defaults require environment-specific testing; none are specified in the uploaded architecture.

### P1-05 — Separate planning, offline implementation, disposable integration, worker activation, and production gates

The acceptance section conflates “accepted for local development” with passing implementation tests. Treat these as different explicit decisions. The uploaded architecture authorizes planning only; no worker startup or database intervention follows from design approval.

## Strengths that should be preserved

1. M2.5 remains the sole human-approval/policy authority and is enforced again at the final provider/tool request.
2. MySQL atomic protocol + audit + outbox persistence; Redis only transports safe identifiers/metadata.
3. Consumer ledger and side effects commit before acknowledgement; a failed XACK is naturally replayable.
4. Recipient eligibility is revalidated at consumption time, preventing stale assignments from retaining authority.
5. Tests cover independent MySQL sessions, crash before/after commit, contention, privacy, and replay.
6. No new public API, historical Alembic edit, or implied production certification.

### A. Exclusive single-writer journal coordination (not implemented/approved)

- Create an OS-appropriate exclusive lock/handle for the journal's entire mutation lifetime, not merely during `os.replace`.
- Bind lock metadata to `rehearsal_id`, journal path, process/instance identity, and an unpredictable run nonce. Lock state alone does not confer execution authority.
- Fail closed on lock contention, ambiguous owner, stale lock, unsupported filesystem, or lock IO failure. No automatic stale-lock break.
- Prefer local filesystems with documented atomic replacement behavior; separately test Windows behavior. Do not claim `os.replace` + fsync proves Windows power-loss durability.
- Require read/verify → compare immutable identity and journal state → atomic write → reload/verify **under one exclusive lock**.
- Tests: competing writers, stale state, process crash and lock release/retention semantics, replay of stale in-memory copy, journal/lock path substitution, and simulated write/reload failures.

### B. Durable PREPARED record before any future statement (not implemented/approved)

Proposed monotonic state model:
`PENDING_REVIEW → PREPARED → PASSED` for a step; on any failure `PREPARED → STOP_NO_RETRY`.

- Persist and reload-verify `PREPARED` *before* a separately approved runner could start a statement.
- Include statement fingerprint, reviewed SQL hash, disposable target identity, operator approval reference, observed preconditions, before-snapshot hash, timestamp, and unique step ID.
- Permit at most one unresolved PREPARED entry. On restart with unresolved PREPARED, **do not execute or retry**; preserve evidence for independent reconciliation.
- Never record `PASSED` unless all observed pre/postconditions pass and all referenced snapshot file hashes are verified against actual files.
- Every terminal stop is immutable and permanently blocks continuation; no automatic rollback or Alembic stamp.
- Tests: crash after PREPARED before statement, crash after committed DDL before result record, fail to persist outcome, unexpected after-snapshot, tampered PREPARED, and second-process racing writer.
