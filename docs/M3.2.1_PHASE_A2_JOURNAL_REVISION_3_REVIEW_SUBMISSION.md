## P1 remediation: orphaned PREPARED ownership

`tools/recovery/m321_step_journal.py` now uses schema version 4 and includes
immutable ownership on every lifecycle action:

- `PREPARED` contains `{epoch, instance_id, run_nonce}`.
- A mutation session reusing the same instance/run nonce may close its own
  persisted `PREPARED` step.
- A different instance or nonce is an orphaned ownership epoch. Its ordinary
  `PASSED`, `STOP_NO_RETRY`, and next-`PREPARED` paths are rejected.
- Only `reconcile_prepared_and_persist()` can continue the lifecycle. It
  appends one durable `RECONCILED` record before any outcome.
- Reconciliation requires an exact prepared-step ID, exact prior ownership,
  independent reviewer ID, approval reference, SHA-256 evidence reference,
  explicit `approved: true`, and observed passing reconciliation checks.
- The reconciler receives a later epoch. The final outcome must reference the
  effective owner, so an old owner cannot append the result after a hand-off.

The resulting lifecycle is append-only and persistence-gated:

```text
PREPARED -> PASSED | STOP_NO_RETRY
PREPARED -> RECONCILED -> PASSED | STOP_NO_RETRY
```

`RECONCILED` is review evidence, never a statement retry. The journal cannot
authenticate a real-world reviewer on its own; a future separately authorized
runner must validate that external authority before supplying the record.

## Windows locking evidence

The lock remains a fixed one-byte OS lock file plus atomic JSON `.lock.meta`
sidecar. The new regression simulates the Windows `msvcrt.locking` path and
verifies that the lock handle receives only `NUL`, while metadata is emitted to
the distinct sidecar as JSON. It also verifies that source does not use append
mode for the lock byte.

This is simulated offline coverage only. Native multi-process Windows
contention, crash leftovers, power loss, AV interference, and filesystem
durability are **not** claimed as passed. The contract remains fail-closed:
stale or ambiguous held metadata is never automatically broken.
