# HEALTHCARE AI DESK

## Product Requirements Document (PRD)

**Version:** 1.0
**Status:** Approved Baseline for Development
**Deployment:** Local-First
**Primary Language:** Khmer
**Secondary Language:** English
**Product Type:** Multi-Agent Healthcare Workflow Platform

---

## 1. Product Overview

Healthcare AI Desk is a locally deployable, multi-agent AI collaboration platform designed for healthcare organizations, public health professionals, healthcare project managers, and medical administrative teams.

Users interact with specialized AI agents through a unified conversational interface.

The platform provides agent management, intelligent task delegation, multi-agent collaboration, persistent memory, document processing, healthcare workflow automation, and human approval.

## 2. Target Users

| User                       | Responsibilities                  |
| -------------------------- | --------------------------------- |
| System Administrator       | System configuration and security |
| Organization Administrator | Organization and user management  |
| Healthcare Manager         | Healthcare workflow management    |
| Project Manager            | Workplans, activities, budgets    |
| Health Data Analyst        | Data analysis and indicators      |
| Clinical Professional      | Review of clinical information    |
| Programme Officer          | Implementation and reporting      |
| General User               | Approved AI-assisted tasks        |

## 3. Product Goals

1. Enable non-technical users to coordinate multiple AI agents.
2. Automate repetitive healthcare administrative tasks.
3. Support MNCH and public health programme management.
4. Improve reporting and monitoring efficiency.
5. Establish a reusable organizational knowledge base.
6. Maintain privacy, accountability, and human oversight.

## 4. Functional Requirements

### FR-001: Authentication

- User registration and login.
- Secure password hashing using Argon2id.
- JWT access tokens.
- Refresh token rotation and revocation.
- Role-based access control.
- Session management.

### FR-002: Organization Management

- Create organizations.
- Manage organizational members.
- Assign organizational roles.
- Enforce organization-level data isolation.

### FR-003: Project Management

- Create healthcare projects.
- Define project descriptions and objectives.
- Assign project members.
- Configure project-specific AI settings.
- Track project status.

### FR-004: Agent Management

- Create and configure AI agents.
- Define names, descriptions, roles, and capabilities.
- Assign agents to projects.
- Configure model providers.
- Configure agent permissions.
- Enable and disable agents.
- Maintain agent version history.

### FR-005: Supervisor

- Receive user instructions.
- Classify tasks.
- Select appropriate agents.
- Delegate tasks.
- Track execution.
- Consolidate results.
- Request human approval.

### FR-006: Group Chat

- Create conversations.
- Add multiple agents.
- Send messages.
- Support agent-to-agent communication.
- Display agent execution status.
- Preserve conversation history.
- Support streaming responses.

### FR-007: Workspace Isolation

- Isolate agent execution environments.
- Prevent conflicting file modifications.
- Maintain execution logs.
- Support approval-controlled file changes.
- Provide rollback capability.

### FR-008: Organizational Memory

- Store approved organizational knowledge.
- Separate project and organizational context.
- Record knowledge sources.
- Support correction and version history.
- Prevent unauthorized memory sharing.

### FR-009: Healthcare Workflows

Initial supported workflows:

- MNCH programme reporting.
- ANC/PNC training coordination.
- Mother class planning.
- Health facility monitoring.
- Workplan management.
- Indicator analysis.
- Research and evidence summaries.
- Project implementation tracking.

### FR-010: Audit and Approval

- Record user and agent activities.
- Record task assignments.
- Record approval decisions.
- Track document changes.
- Require human approval for sensitive operations.

## 5. Non-Functional Requirements

| Category        | Requirement                          |
| --------------- | ------------------------------------ |
| Security        | Authentication, RBAC, encryption     |
| Privacy         | Patient data minimization            |
| Reliability     | Retry, timeout, error recovery       |
| Scalability     | Modular services                     |
| Performance     | Responsive interface                 |
| Maintainability | Modular codebase                     |
| Observability   | Structured logs and metrics          |
| Localization    | Khmer and English                    |
| Deployment      | Local Docker environment             |
| Testing         | Automated unit and integration tests |

## 6. Healthcare Safety Requirements

- The system is a decision-support and administrative assistant, not an autonomous healthcare provider.
- No autonomous diagnosis or prescription.
- No autonomous clinical intervention.
- Clinical content must identify its source and publication date.
- Use verified Ministry of Health, WHO, and UNICEF guidance where applicable.
- Urgent danger signs must trigger clear referral guidance to qualified healthcare professionals.
- Patient-identifiable data must not be submitted to external LLM providers without an authorized, legally compliant data-processing arrangement.
- Human review is mandatory for clinical content intended for operational use.

## 7. MVP Acceptance Criteria

The initial platform is accepted when:

- Users can authenticate securely.
- Organizations and projects can be created.
- Database migrations execute successfully.
- Users can manage project membership.
- The frontend connects to the backend.
- Agent registry foundation is available.
- Audit events are recorded.
- Docker deployment works locally.
- Automated tests pass.
- Installation and recovery instructions are documented.

## 8. Out of Scope for M1

- Autonomous clinical decisions.
- Full multi-agent conversations.
- Production healthcare RAG.
- Automatic clinical record integration.
- Autonomous external system operations.
- Fully automated document publication.

These capabilities will be delivered in subsequent milestones.

## 5.3 Important Database Design Rules

1. All project-related records must have an organization ownership boundary.
2. Every query must validate organization membership and authorization.
3. Passwords and API secrets must never be stored in plaintext.
4. Conversation messages must be append-only from the normal application workflow.
5. Approval decisions must be immutable audit events.
6. Soft deletion must be used where appropriate.
7. Use foreign keys and database indexes.
8. Use UTC timestamps in storage and localize timestamps in the interface.
9. Patient data must not be included in generic agent memory.
10. Database migrations must be version-controlled.

## 5.4 Initial SQL Migration — M1

The following is the initial database foundation. UUIDs are stored as `CHAR(36)` for readability and portability.

```
CREATE DATABASE healthcare_ai_desk
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

USE healthcare_ai_desk;

CREATE TABLE users (
    id CHAR(36) PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    full_name VARCHAR(150) NOT NULL,
    preferred_language VARCHAR(10) DEFAULT 'km',
    status ENUM('active','inactive','locked')
        DEFAULT 'active',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE organizations (
    id CHAR(36) PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    slug VARCHAR(100) NOT NULL UNIQUE,
    status ENUM('active','inactive')
        DEFAULT 'active',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE organization_members (
    id CHAR(36) PRIMARY KEY,
    organization_id CHAR(36) NOT NULL,
    user_id CHAR(36) NOT NULL,
    role ENUM(
        'owner',
        'admin',
        'manager',
        'member',
        'viewer'
    ) NOT NULL DEFAULT 'member',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    UNIQUE KEY uq_org_user (organization_id,user_id),

    FOREIGN KEY (organization_id)
        REFERENCES organizations(id),
    FOREIGN KEY (user_id)
        REFERENCES users(id)
);

CREATE TABLE projects (
    id CHAR(36) PRIMARY KEY,
    organization_id CHAR(36) NOT NULL,
    name VARCHAR(200) NOT NULL,
    description TEXT,
    status ENUM(
        'draft',
        'active',
        'completed',
        'archived'
    ) DEFAULT 'draft',
    created_by CHAR(36) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    INDEX idx_project_org (organization_id),

    FOREIGN KEY (organization_id)
        REFERENCES organizations(id),
    FOREIGN KEY (created_by)
        REFERENCES users(id)
);

CREATE TABLE project_members (
    id CHAR(36) PRIMARY KEY,
    project_id CHAR(36) NOT NULL,
    user_id CHAR(36) NOT NULL,
    role ENUM('manager','member','viewer')
        DEFAULT 'member',
    UNIQUE KEY uq_project_user (project_id,user_id),

    FOREIGN KEY (project_id)
        REFERENCES projects(id),
    FOREIGN KEY (user_id)
        REFERENCES users(id)
);

CREATE TABLE audit_logs (
    id CHAR(36) PRIMARY KEY,
    organization_id CHAR(36) NOT NULL,
    actor_type VARCHAR(30) NOT NULL,
    actor_id CHAR(36),
    action VARCHAR(100) NOT NULL,
    resource_type VARCHAR(100),
    resource_id CHAR(36),
    metadata JSON,
    ip_address VARCHAR(45),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    INDEX idx_audit_org_time
        (organization_id,created_at)
);

CREATE TABLE refresh_tokens (
    id CHAR(36) PRIMARY KEY,
    user_id CHAR(36) NOT NULL,
    token_hash VARCHAR(255) NOT NULL,
    expires_at DATETIME NOT NULL,
    revoked_at DATETIME NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    INDEX idx_refresh_user (user_id),

    FOREIGN KEY (user_id)
        REFERENCES users(id)
);
```

## 6.5 M1 Acceptance Gate

M1 cannot be marked complete merely because the interface looks functional.

The acceptance gate requires:

1. Actual database persistence.
2. Actual authentication verification.
3. Actual authorization enforcement.
4. Automated test evidence.
5. Successful local deployment.
6. No unresolved critical security defects.

Only after this gate passes should M2 begin.
