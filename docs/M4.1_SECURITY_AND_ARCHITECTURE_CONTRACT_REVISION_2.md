# Healthcare AI Desk — M4.1 Security & Architecture Contract, Revision 2

**Status:** Review-only architecture contract; pending independent re-review.
**Execution authorization:** `false`.
**Supersedes:** M4.1 Revision 1 for all M4.1 requirements.
**Safety authority:** M2.5 remains the only high-impact approval and
external-provider egress authority.

Revision 2 incorporates the P1 clarifications from the Revision 1 independent
architecture review. It is a design contract, not M4.2 authorization or
evidence that any database, Qdrant, provider, worker, or API implementation
exists.

## 1. Non-negotiable security properties

1. MySQL is authoritative for identities, RBAC/assignment state, ACLs,
   document/version lifecycle, classification, retention/legal hold,
   revocation, generation activation, idempotency receipts, and audit.
2. Qdrant is a rebuildable candidate index, never an authority for access,
   revocation, lifecycle, approval, or high-impact execution.
3. Client, agent-message, cache, Qdrant payload, and vector-score fields are
   untrusted and cannot expand tenant, project, document, or provider access.
4. No candidate can disclose text, title, locator, score, count, existence, or
   derivative context until the post-search and final-disclosure MySQL checks
   both succeed.
5. Patient-restricted data are denied from generic shared memory, Qdrant, and
   external embedding/LLM routes. Ambiguous classification fails closed.
6. Retrieved content is untrusted data. It cannot create tool, RBAC, agent,
   provider, approval, or clinical-decision authority.

## 2. Classification and protected preprocessing (P1-D)

### 2.1 Initial classification scope

| Classification | Initial M4.1 disposition |
| --- | --- |
| `public_within_org` | Eligible only with organization, purpose, ACL, and lifecycle authorization. |
| `project_restricted` | Eligible only with an active server-derived project grant. |
| `clinical_reference` | Eligible only when approved/effective/current and complete provenance/citation governance exists. |
| `confidential` | Denied until separately designed and approved. |
| `patient_restricted` | Denied from generic memory/index/egress. |

### 2.2 Untrusted intake and quarantine pipeline

Uploaded files, extracted text, images, archives, and OCR inputs are untrusted.
Detection cannot be assumed to happen before parsing. The required pipeline is:

```text
untrusted intake
  → immutable intake receipt + malware/type/size gate
  → private local quarantine
  → least-privilege parser/OCR/extractor with CPU/time/memory/output limits
  → classification and PII/PHI detection
  → required redaction/minimization and authoritative review/approval
  → immutable approved source version
  → permitted local/external embedding route and indexing
```

Quarantine is isolated from generic application, analytics, provider, and
search paths. Parser/OCR workers have no outbound provider credentials, no
retrieval credentials, and access only to one leased object and an approved
local output location. Temporary files, page renders, OCR outputs, debug
traces, exception logs, caches, and observability payloads must be encrypted
where retained, access controlled, retention-bounded, and excluded from generic
support access. Failure, timeout, uncertain classification, failed redaction,
or unavailable required policy/scan produces `QUARANTINED`/`DENIED`, not an
indexable version.

## 3. Server-owned authorization and visibility predicate (P1-A)

### 3.1 Authorization context

The server constructs a short-lived immutable context from authenticated and
authoritative state:

```text
principal_id + principal_type
organization_id
permitted_project_ids
purpose_of_use
role/assignment/clearance generation
agent profile/version/active assignment, if applicable
request_id + correlation_id
authorization generation + policy version
```

It is never accepted from client fields, agent messages, Qdrant payloads, or
cache entries. Reuse across a principal, purpose, organization, project set,
or authorization-generation change is forbidden.

### 3.2 Required MySQL predicate

For every candidate, MySQL must evaluate the following grouped predicate under
the authoritative organization scope. The visibility `OR` is the **only** OR
group; all remaining predicates are mandatory outside it.

```text
candidate.organization_id = context.organization_id
AND version.lifecycle = APPROVED_ACTIVE
AND version.effective_at <= database_now
AND (version.expires_at IS NULL OR database_now < version.expires_at)
AND version.revocation_generation = authoritative_current_generation
AND version.index_visibility_state = ACTIVE
AND candidate.index_generation = version.active_index_generation
AND classification_allows(context.purpose_of_use)
AND legal_hold_state_allows_retrieval
AND (
      (candidate.visibility = organization_wide
       AND organization_scope_permits(context))
   OR (candidate.visibility = project_restricted
       AND candidate.project_id IN context.permitted_project_ids)
    )
AND active_acl_grant_permits(context.principal_id, context.purpose_of_use)
AND effective_agent_assignment_permits_if_applicable(context)
```

Repository code must bind server-resolved values, reject malformed project IDs,
and use organization-scoped joins/foreign keys. It must not implement this as
post-filtering after fetching text. Organization-wide visibility does not
bypass ACL, assignment, purpose, lifecycle, classification, legal-hold, or
generation checks.

### 3.3 Qdrant candidate query

Qdrant queries carry compulsory server-derived organization and visibility
filters and current index-generation conditions. Qdrant may return only opaque
point, document-version, chunk, organization, and generation identifiers.
Plaintext chunks, patient identifiers, titles, citation URLs, and user-facing
ACL values are not stored in initial Qdrant payloads.

Qdrant filtering reduces candidate volume; it never replaces §3.2. A remote
Qdrant deployment, vector telemetry, backup, snapshot, or managed support
channel is a data destination and must be classified/authorized under §5.

## 4. Two-stage disclosure consistency and revocation race (P1-B)

### 4.1 Post-search authorization

After Qdrant returns IDs, MySQL evaluates §3.2 before fetching any bounded
authoritative chunk text. Unauthorized, stale, missing, revoked, expired,
superseded, or ambiguous candidates are omitted without revealing their title,
score, locator, count, existence, or denial reason.

The service records an in-memory `DisclosureFence` for each allowed candidate:

```text
document_version_id, chunk_id, ACL/assignment generation,
revocation_generation, active_index_generation, authorization_generation,
authorized_at, bounded result/context budget
```

The fence is not a reusable authorization token and is not cached as a grant.

### 4.2 Final-disclosure boundary

After response assembly and immediately before the first byte, citation, or
streamed token is emitted, the service repeats the authoritative generation,
ACL, assignment, lifecycle, classification, effective/expiry, legal-hold, and
active-index checks for every disclosure-fence item. Only the set that passes
this final check may be emitted.

For non-streaming output, the final check and response construction use one
short read-consistency boundary appropriate to the verified MySQL isolation
mode; the implementation must document the exact transaction/isolation choice.
The implementation cannot rely on a cached authorization result.

For streaming output, the service retains the fence and checks it before each
new protected chunk/citation/context segment is released. On observed ACL,
assignment, lifecycle, revocation, or generation change, it must stop output,
close/cancel the stream where possible, prevent further protected text from
being emitted, and audit the interruption. Bytes already delivered cannot be
retracted; the design therefore requires the final check before first output
and forbids pre-authorized buffered disclosure.

## 5. Revocation, replay, receipt, and activation fencing (P1-E)

### 5.1 Authoritative generations

Document versions maintain MySQL-authoritative lifecycle and monotonically
increasing `revocation_generation` and `active_index_generation`. Revocation,
expiry, supersession, ACL withdrawal, or approval withdrawal updates the
relevant generation/lifecycle and emits the durable outbox intent in one
transaction. Read authorization denies obsolete generations immediately;
physical Qdrant purge is eventual cleanup, not a permission boundary.

### 5.2 Idempotent receipt identity

The M4.2 schema must enforce an organization-scoped immutable uniqueness key
equivalent to:

```text
(organization_id, document_version_id, chunk_id,
 embedding_model_version, collection_schema_generation, index_generation)
```

The receipt stores point ID, source/redacted chunk hash, expected revocation
generation, processing provenance, state, and minimal error code. Receipt
insertion and logical activation state changes are transactional MySQL actions;
duplicate-key conflicts are classified as expected replay only after verifying
the immutable identity/provenance agrees. Other integrity failures raise.

### 5.3 Activation compare-and-swap

Workers write only a non-active/staged generation until MySQL atomically
compares the expected lifecycle, revocation generation, and prior active index
generation, then marks the requested generation `ACTIVE`. A conceptual CAS is:

```text
UPDATE document_versions
SET active_index_generation = :requested_generation,
    index_visibility_state = 'ACTIVE'
WHERE organization_id = :organization_id
  AND id = :document_version_id
  AND lifecycle = 'APPROVED_ACTIVE'
  AND revocation_generation = :expected_revocation_generation
  AND active_index_generation < :requested_generation;
```

Zero updated rows means stale/superseded/revoked work: it cannot become active,
must not be acknowledged as active, and must create/retain a scoped purge
intent. Old physical points may remain transiently but are non-retrievable
through §3 and §4.

The consumer commits MySQL receipt/activation outcome before Redis `XACK`.
After a crash or failed acknowledgement, reclaimed delivery repeats idempotent
receipt/CAS logic. Tests must cover commit-before-XACK, retry, duplicate
delivery, revoke before/after Qdrant upsert, and an old worker after a newer
generation becomes active.

## 6. Exact egress binding and external-boundary policy (P1-C)

### 6.1 Covered destinations

The policy applies to user/agent query embeddings, document/chunk embeddings,
metadata/title/summaries, reranking, final LLM context, remote vector indexes,
telemetry, backups, support diagnostics, and any provider SDK call that may
transmit a representation of protected content.

Local components remain subject to access control and audit. A component is
not considered local merely because its API is private: deployment location,
network path, operator access, backup path, telemetry, and retention determine
whether it is an external destination.

### 6.2 One-use decision binding

Before non-local egress, M4 requests an M2.5 decision bound to:

```text
egress_attempt_id + operation_id + operation_type
canonical input payload SHA-256 + post-redaction payload SHA-256
classification/redaction policy and version
principal, organization, purpose, and agent context
provider, endpoint, model, region, retention/no-training terms
destination type, byte/token budget, decision policy/version
issued_at, expiry, and single-use flag
```

The egress sender verifies the decision immediately before transmission. Any
change to retrieved candidates, chunk/query text, redaction result, payload
hash, operation, provider, endpoint, model, region, retention terms, or
destination invalidates the decision and requires a new M2.5 evaluation.

`deny`, `approval_required`, unavailable policy, failed redaction, or expired/
used decision causes a fail-closed denial. There is no automatic provider,
region, model, retention, local/remote, or classification downgrade fallback.
Audit stores only identifiers, hashes, policy result, and correlation data—not
raw query/chunk text, credentials, or patient identifiers.

## 7. Immutable source, provenance, and clinical governance

Each indexable version requires authorized encrypted source-object reference and
key reference, source SHA-256, issuer/license/acquisition/citation locator,
classification/visibility, extractor-OCR-chunker/redaction versions and hashes,
embedding model/version, collection schema generation, and requested index
generation. Encryption/key lookup, source integrity, extraction, redaction, or
provenance failure has no plaintext fallback and cannot yield an active index.

Chunk identity is deterministic from tenant-scoped document version, ordinal,
source locator, extractor/chunker version, and redaction version. Point identity
is deterministic from chunk identity, embedding model version, collection
schema generation, and index generation. MySQL owns the mapping and uniqueness
constraints; Qdrant does not choose IDs.

Clinical references additionally require issuer, jurisdiction, accountable
clinical reviewer, approval/effective/expiry/review dates, supersession state,
license, and edition-specific citation locator. Similarity does not establish
clinical correctness. Citations must not imply patient-specific diagnosis,
treatment, prescribing, or approval authority.

## 8. Governance ownership and M4.2 preconditions (P1-F)

Before M4.2 planning is accepted, an approved, version-controlled decision
record must name responsible owner/approver ID and decision reference for each:

| Decision area | Required accountable record |
| --- | --- |
| Schema compatibility | MySQL/Alembic head, tenant composite keys/types/collations, forward-only strategy. |
| Qdrant boundary | Deployment/collection isolation, authn/authz, TLS/network, payload policy, backups, restore/rebuild, support access. |
| M2.5 integration | Classification matrix, operation-to-policy mapping, local/external destinations, provider/region/retention terms, denial/fallback behavior. |
| Data protection | Key ownership/rotation, quarantine, detection/redaction exception path, audit access, telemetry and backup handling. |
| Clinical governance | Reviewer, jurisdiction, licensing, reference approval/effective/expiry/supersession cadence. |
| Retention and legal hold | Retention owner, deletion/purge approval, hold precedence, backup expiry, minimum audit record. |
| Testing authorization | Synthetic-fixture approval, disposable environment identity, no shared-volume/reset boundary, reviewers. |

The absence, expiry, or mismatch of any required decision record blocks M4.2.

| ID | Required evidence |

| M4-T01 | Negative repository tests prove grouped visibility predicate, forged tenant/project rejection, ACL enforcement, and active agent assignment checks. |
| M4-T02 | Revoked Qdrant candidate exposes zero protected text, title, score, locator, count, or existence signal. |

| M4-T05 | Commit-before-XACK, replay, rebuild, and duplicate delivery yield one matching immutable receipt/point identity. |
| M4-T06 | Query/chunk/metadata/reranker/final-context/remote-index egress denies provider failover, post-redaction mutation, expired decision, and leakage. |
| M4-T07 | Retrieved prompt-injection content cannot grant tools, providers, RBAC, routing, or approval authority. |
| M4-T08 | Expired/superseded/unapproved/provenance-incomplete clinical content is excluded from citation. |

Tests use only synthetic data. No test may be marked passed without execution
evidence from the separately authorized disposable environment.

## 10. Decision

Revision 2 incorporates P1-A through P1-F at design-contract level and is
ready for independent re-review. M4.2 schema planning remains **blocked** until
that review accepts this revision and §8 decision records are approved. No
infrastructure, migration, ingestion, Qdrant, provider egress, or shared data
operation is authorized.
