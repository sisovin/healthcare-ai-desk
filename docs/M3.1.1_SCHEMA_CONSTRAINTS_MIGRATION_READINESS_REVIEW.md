## 4. Constraint review

### 4.1 Tenant and project boundaries

- `conversations` has unique `(organization_id, id)` and a composite foreign key from `(organization_id, project_id)` to `projects`.
- Child conversation tables use composite `(organization_id, conversation_id)` foreign keys to prevent cross-tenant/conversation attachment.
- Agent references use tenant composite foreign keys to `(agent_profiles.organization_id, agent_profiles.id)`.
- Repository/API queries scope by organization and require active user membership in the conversation for reads and message writes.

### 4.2 Conversation membership integrity

`conversation_members` has the following effective rule:

```text
(member_type = 'user'  AND user_id IS NOT NULL AND agent_profile_id IS NULL)
OR
(member_type = 'agent' AND user_id IS NULL     AND agent_profile_id IS NOT NULL)
```

It also has uniqueness constraints on:

- `(organization_id, conversation_id, user_id)`
- `(organization_id, conversation_id, agent_profile_id)`

This prevents a membership row from representing both identities or neither, and prevents repeated registration of the same participant in a conversation.

### 4.3 Message integrity, idempotency, and ordering

- Server-owned `sequence_number` is unique per `(organization_id, conversation_id)`.
- `idempotency_key` is unique per `(organization_id, conversation_id)`.
- `request_fingerprint` distinguishes a legitimate repeat from reuse of the same idempotency key with different content.
- Sender identity is exclusive: user, agent, or system, with no ambiguous combination.
- API clients do not supply sequence number, status transition, approval state, provider route, or agent execution state.

### 4.4 Task dependency integrity

`conversation_task_dependencies` contains:

```text
id
organization_id
conversation_id
task_id
depends_on_task_id
created_at
```

It enforces:

- unique `(organization_id, task_id, depends_on_task_id)`;
- `task_id <> depends_on_task_id`;
- composite tenant/conversation foreign keys for both the dependent task and prerequisite task;
- multiple prerequisite rows for a single task.

The current schema supports a task such as `generate-report` depending on both `validate-data` and `review-data`. Cycle detection and same-plan validation remain Supervisor plan/service responsibilities in M3.1.3 because M3.1.1 has no plan persistence/execution service yet.

## 5. Conversation privacy review

### Current implementation behavior

1. User input is classified at message persistence time.
2. Email, Cambodian-format phone numbers, and configured patient-identifier patterns are redacted in the API-visible `content_redacted` value.
3. The original local message is stored in `content_ciphertext` using Fernet encryption.
4. Audit metadata records classification and sequence only; it does not contain the raw message, PII, or ciphertext.
5. No M3.1.1 API decrypts or returns `content_ciphertext`.

### Required deployment control

`CONVERSATION_ENCRYPTION_KEY` must be set to a dedicated deployment-managed secret in production. Local/test fallback behavior derives an encryption key from `APP_SECRET_KEY`; it is not an approved production key-management configuration.

### External LLM boundary

M3.1.1 does not call an LLM. M2.5 remains the required final egress gate for all future LLM/tool calls. M3.1.3 must invoke that gate before creating runnable high-impact work; M3.1.1 task persistence does not create a safety bypass.

## 6. State/concurrency review

- `conversations.state_version` and `conversation_tasks.state_version` are persisted with checks requiring values of at least one.
- The message service validates `expected_state_version`, locks the conversation row, increments version atomically with message/audit persistence, and returns a conflict on stale state.
- Identical duplicate message requests return the original persisted message; same idempotency key with different content returns conflict.
- M3.1.1 does not expose an API to set `processing`, `waiting_approval`, or terminal workflow state. Those server-owned transitions remain M3.1.3 coordinator work.

## 7. API compatibility review

The following endpoints are additive under `/api/v1/conversations`:

- `POST /api/v1/conversations`
- `GET /api/v1/conversations`
- `GET /api/v1/conversations/{id}`
- `POST /api/v1/conversations/{id}/messages`
- `GET /api/v1/conversations/{id}/messages`

Existing M1/M2/M2.5 endpoint paths and response contracts were not edited. Conversation permissions were added to the existing role mapping without removing any pre-existing permission.
