# Healthcare AI Desk — M4.1 Security & Architecture Contract, Revision 1

**Status:** Review-only architecture contract.
**Execution authorization:** `false`.
**Implementation status:** No M4 schema, Qdrant collection, ingestion worker,
embedding route, or retrieval API is created by this document.
**Supersedes for M4.1:** The high-level M4 plan where this contract is more
specific.
**Safety authority:** M2.5 remains the only authority for high-impact approval
and external-provider egress.

## 1. Binding security properties

M4.1 governs retrieval of approved organizational and healthcare-reference
knowledge. It does not make retrieved information an execution authority,
clinical decision, or approval decision.

The implementation must satisfy all of the following:

1. MySQL is authoritative for identity, assignments, ACLs, document/version
   lifecycle, classification, effective dates, legal holds, revocation, and
   indexing generations. Qdrant is a rebuildable candidate index only.
2. Every request is server-bound to an authenticated principal, organization,
   permitted project set, purpose, and authorized agent context. Client-sent
   tenant, ACL, score, or sequence fields are untrusted hints and cannot widen
   access.
3. Qdrant results are candidates only. A MySQL reauthorization occurs **after
   search and before any chunk text, payload, citation locator, or result count
   derived from a protected hit is disclosed**.
4. Revocation is immediate at the MySQL decision point. Eventual vector purge
   never delays authorization denial.
5. Query embedding, document embedding, reranking, and final LLM context
   egress use class-specific M2.5 decisions. No denied route may fall back to a
   weaker provider, model, or retention arrangement.
6. Every indexed point is reproducible from an approved immutable source
   version and recorded processing provenance.

## 2. Scope and classification

Initial M4.1 retrieval scope is limited to the following server-owned
classifications:

| Classification | Initial handling |
| --- | --- |
| `public_within_org` | Eligible only after organization/purpose authorization. |
| `project_restricted` | Eligible only if the requested project is an active allowed scope. |
| `clinical_reference` | Eligible only if approved, effective, not superseded/revoked, and citation provenance is complete. |
| `confidential` | Deny by default until a separate access and egress design is approved. |
| `patient_restricted` | Deny by default. Not stored in generic shared memory, Qdrant, or any external embedding route. |

The server performs PII/PHI classification before extraction, chunking, audit,
embedding, index write, or provider egress. A detection failure, ambiguous
classification, policy-service failure, or unavailable required redaction must
fail closed for the protected route and create minimal diagnostic audit data.

## 3. Authoritative identity and authorization contract

### 3.1 Server-owned request context

The retrieval service builds an immutable `RetrievalAuthorizationContext` from
the authenticated request and authoritative services:

```text
principal_id
principal_type (user | service | agent)
organization_id
permitted_project_ids
purpose_of_use
active_role_and_assignment_snapshot
agent_profile/version/assignment, when agent initiated
request_id + correlation_id
policy_version + authorization_generation
```

The context is not supplied by a browser, agent message, Qdrant payload, or
cached request body. It is short-lived and cannot be reused across tenants,
principals, purposes, or authorization-generation changes.

### 3.2 Explicit visibility predicate

For a candidate to be disclosed, MySQL must prove all of these predicates:

```text
candidate.organization_id == context.organization_id
AND candidate.document_version.lifecycle == APPROVED_ACTIVE
AND candidate.document_version.effective_at <= database_now
AND (candidate.document_version.expires_at IS NULL
     OR database_now < candidate.document_version.expires_at)
AND candidate.document_version.revocation_generation == current_generation
AND candidate.document_version.legal_hold_state permits the requested operation
AND candidate.classification is allowed for context.purpose_of_use
AND candidate.visibility is organization-wide
    OR candidate.project_id IN context.permitted_project_ids
AND an active ACL grant permits context.principal and purpose
AND, for an agent, active published assignment/capability permits retrieval
```

The actual SQL/repository implementation must parenthesize the visibility
predicate so organization-wide visibility cannot bypass the preceding tenant,
lifecycle, classification, ACL, or purpose checks.

### 3.3 Required post-Qdrant reauthorization (M4-D01)

The Qdrant request uses mandatory organization and server-derived visibility
filters, but this is defense in depth only. Qdrant should return no plaintext
chunk content to the caller; candidate payload is restricted to opaque point,
document-version, chunk, and index-generation identifiers.

Immediately after search, the service uses MySQL to fetch only the candidates
under the authoritative predicate above. It rechecks current principal state,
role/assignment, ACL, document-version approval, classification, effective and
expiry dates, current revocation generation, legal hold, and active index
generation. Only then may it fetch bounded authoritative chunk text and create
citations.

If a candidate is absent, stale, unauthorized, revoked, expired, superseded,
or ambiguous, it is silently omitted from the result. The service must not
reveal its title, locator, score, count, existence, or reason to an
unauthorized caller. An empty authorized result is preferable to a cross-scope
fallback.

The final response is assembled from the post-check authorized set. Any cache
stores only scope-safe identifiers and must key/invalidate by organization,
principal/purpose scope, document version, authorization generation, and
revocation generation. Cached text cannot bypass the post-hit check.

## 4. Revocation and index-generation fencing (M4-D02)

### 4.1 Authoritative state

Each document version has immutable content/provenance plus mutable,
authoritative lifecycle fields:

```text
lifecycle                    APPROVED_ACTIVE | REVOKED | EXPIRED | SUPERSEDED | DELETED
revocation_generation        monotonically increasing positive integer
active_index_generation      monotonically increasing positive integer
index_visibility_state       PENDING | ACTIVE | BLOCKED | PURGE_PENDING | PURGED
```

Revocation, expiry, supersession, or ACL withdrawal increments the relevant
authorization/revocation generation in the same MySQL transaction that records
the lifecycle decision and durable outbox event. Retrieval rejects the old
generation immediately; no Redis, Qdrant, or worker acknowledgement is needed
to make the decision effective.

### 4.2 Index worker fence

Every indexing/reindexing event contains document version ID, expected
`revocation_generation`, requested `index_generation`, source/provenance hash,
and idempotency key. The worker must:

1. lease the event through the existing durable outbox contract;
2. read the authoritative version and verify it is still `APPROVED_ACTIVE` and
   generation-equal before vector construction;
3. perform a second authoritative generation/lifecycle check immediately before
   making a point searchable;
4. write deterministic point IDs and payload containing organization ID,
   project visibility marker, document version ID, chunk ID, and index
   generation—never raw chunk text or patient identifiers;
5. record an idempotent receipt only if the authoritative generation remains
   current; otherwise mark the stale event suppressed and issue/retain a purge
   intent where required.

Concurrent revocation wins. A late worker may leave a transient stale physical
point only until purge, but it cannot make that point retrievable because both
mandatory Qdrant filters and the final MySQL authorization reject the obsolete
generation. Purge/rebuild completion is audited, monitored, and retryable; it
does not change the immediate deny decision.

## 5. Embedding, reranking, and LLM egress policy (M4-D03)

### 5.1 Covered operations

The egress contract applies independently to:

- user/agent retrieval queries;
- source documents and extracted chunks;
- chunk summaries, metadata, or title fields;
- reranker requests;
- retrieved context passed to a generative LLM.

“Embedding” does not create an exception to PII/PHI policy. A vector, hash,
or summary may remain sensitive and must follow the governing classification.

### 5.2 M2.5 decision input and outcome

Before any non-local provider call, M4 requests an M2.5 egress decision using
the authoritative classification, caller/purpose, tenant policy, destination
provider/region, model, operation type, approved retention/no-training terms,
redaction requirement, payload byte/token budget, and correlation ID.

Allowed decisions must be explicit for the exact operation and payload class.
The audit record stores only decision ID, policy/version, provider/model
identifier, payload classification, redaction outcome/hash, and correlation ID;
it never stores raw query/chunk text, credentials, or patient identifiers.

| Decision | Required behavior |
| --- | --- |
| `allow_local` | Process only through the approved local route, with normal ACL/audit controls. |
| `allow_external_redacted` | Apply approved redaction/minimization, verify it succeeded, then send only the approved representation. |
| `deny` / `approval_required` / `unavailable` | Do not send payload, do not queue a fallback, and return a policy-safe denial/pending result. |

M4 cannot approve an egress request, change a policy decision, or substitute a
provider. A retry repeats the same or stricter M2.5 evaluation; provider
fallback cannot lower classification, omit redaction, or relax region/retention
terms.

## 6. Immutable source and rebuild provenance (M4-D04)

### 6.1 Authoritative source record

An indexable document version requires:

```text
organization_id, document_id, document_version
encrypted_source_object_reference and key_reference
source_content_sha256
source issuer, license, acquisition time, canonical citation/locator
classification and approved visibility scope
clinical reviewer, approval/effective/expiry/review dates where clinical
extractor version, parser/OCR version, chunking configuration version
PII classification/redaction policy and redacted-content hash
embedding provider/model/version or approved local-model version
Qdrant collection schema generation and requested index generation
```

Original content is read only from authorized encrypted source-object storage.
No plaintext fallback is allowed after encryption, key-resolution, integrity,
or source-hash verification failure. The ingestion pipeline verifies the source
hash before extraction and the extracted/redacted chunk hash before embedding.

### 6.2 Deterministic chunk and point identities

Chunk identity is deterministic from the tenant-scoped document version,
ordinal, source locator, extractor/chunker version, and redaction version.
Point identity is deterministic from the chunk identity, embedding model
version, collection schema generation, and index generation. The database owns
the identity mapping and uniqueness constraint; Qdrant does not choose it.

This allows rebuild into a new generation without accidental overwrite,
cross-version collision, or duplicate logical chunk. A rebuild reads only
approved, current authoritative source versions and records the source hash,
pipeline/model versions, collection schema generation, point ID, and receipt.

### 6.3 Clinical governance

Clinical reference retrieval requires issuer, jurisdiction, reviewer,
approval/effective/expiry/review dates, supersession status, source license,
and citation locator. Similarity score never establishes clinical correctness.
A revoked, expired, superseded, unapproved, or provenance-incomplete reference
is excluded before text or citation disclosure.

## 7. Durable state, audit, and privacy

- MySQL document/version, ACL, lifecycle, audit, and outbox changes that
  represent one action commit or roll back together.
- Qdrant and Redis are not used as the authority for access, revocation,
  lifecycle, or audit completion.
- Outbox delivery is at least once; indexer consumers and receipts must be
  idempotent under duplicate/replayed delivery.
- Audit records are append-only/minimal and use actor, purpose, policy decision,
  opaque object IDs, generations, provenance IDs, correlation ID, and error
  codes. They exclude raw chunks, user queries, credentials, and patient data.
- Source, chunk, vector payload, audit, and administration access use separate
  least-privilege permissions. Qdrant service credentials cannot authorize a
  user-facing retrieval request.
- Legal hold blocks deletion/purge that would destroy required authoritative
  evidence. Revocation can still block retrieval immediately. Retention and
  purge outcome are auditable and preserve required minimal audit history.

## 8. Required test contract (future implementation evidence)

| ID | Required assertion |
| --- | --- |
| M4-T01 | Forged organization/project/ACL input cannot widen request-builder scope or post-hit authorization. |
| M4-T02 | A Qdrant candidate for a revoked version discloses zero chunk text, citation locator, title, score, or existence signal. |
| M4-T03 | ACL/assignment withdrawal between vector lookup and response assembly discloses zero protected text. |
| M4-T04 | A leased indexing event becomes stale after revocation; its worker cannot activate/recreate a searchable current-generation point. |
| M4-T05 | Duplicate outbox delivery/rebuild produces one logical point/receipt per deterministic identity. |
| M4-T06 | Restricted query, chunk, metadata, and reranker payload are denied for external egress; no weaker fallback is attempted. |
| M4-T07 | Retrieved prompt-injection text cannot create provider, tool, RBAC, approval, or agent-routing authority. |
| M4-T08 | Superseded, expired, unapproved, or provenance-incomplete clinical references are excluded from active citations. |
| M4-T09 | Source hash, extracted/redacted chunk hash, processing versions, model version, point ID, and citation locator agree during rebuild. |
| M4-T10 | Legal hold, retention, revocation, deletion, audit, and index-purge states remain consistent and tenant isolated. |

All fixtures are synthetic and contain no real patient data. Cross-tenant,
revocation-race, and egress-denial tests require an authorized disposable
environment before they can be marked passed.

## 9. M4.2 entry gate

M4.2 schema/migration planning may begin only after an independent reviewer
accepts this contract and the following decisions are recorded:

1. exact MySQL/Alembic head, relevant existing keys/column types, and M1–M3
   compatibility constraints;
2. Qdrant authentication, collection strategy, network boundary, backup,
   rebuild, payload minimization, and tenant-filter enforcement design;
3. approved classification matrix, PII/PHI detection failure behavior, local
   and external embedding routes, and M2.5 policy-owner mapping;
4. source-object encryption/key rotation, licensing, clinical governance,
   retention/legal-hold/deletion, and audit ownership;
5. forward-only migration, disposable rehearsal, and no-shared-volume
   execution plan.

## 10. Decision

Revision 1 closes the M4-D01 through M4-D04 architecture decisions at contract
level. It authorizes **only independent review of this design**. It does not
authorize M4.2 implementation, schema changes, infrastructure, ingestion,
embedding, retrieval, or any data egress.
