# M2.5 — LLM Provider Gateway, Agent Tool Execution & Safety Package

## Purpose

M2.5 is the mandatory gateway between Agent Management (M2) and Supervisor & Multi-Agent Group Chat (M3). It supplies provider-independent LLM routing and allow-listed tool execution, while preserving runtime-enforced healthcare safety controls. M3 must not make a provider call until it passes through this gateway.

## LLM provider gateway

- `LLMGateway` routes a request by required capability, configured availability, provider preference, priority, and estimated per-token cost.
- Adapters are included for OpenAI chat completions, Anthropic Messages, and local Ollama chat. They use an injected JSON transport; `UrllibJsonTransport` is available for approved production wiring, while tests use mocks.
- A provider failure retries through the next eligible route up to the caller's attempt limit. Provider error, selected model, token usage, estimated USD cost, and fallback count are supplied to an audit sink.
- Provider SDKs are not required in the domain layer. API keys and endpoint wiring remain deployment configuration, not agent prompts or database records.

## Agent Tool Registry & execution boundary

- `AgentToolRegistry` contains only application-registered tool definitions. Agents cannot execute arbitrary shell commands, paths, or code.
- Each tool declares a required permission, request timeout, input-byte limit, and output-byte limit.
- `ToolExecutionSandbox` checks the allow-list and caller permission before invocation, applies a response deadline, caps serialized input/output, and emits audit events.
- The API-level sandbox is deliberately not a substitute for OS isolation. Any tool processing untrusted content must run in a separate container with CPU/memory/cgroup and network egress restrictions configured by deployment.

## Delivered controls

### Human approval for high-impact actions

- Runtime classifies high-impact task types, including clinical triage, diagnosis, prescription/medication, referral, treatment/care plans, patient-record actions, publication, sending, deletion, payments, and access grants.
- Such executions start in `waiting_approval`; a pending approval record and audit event are created automatically.
- The execution cannot transition to `running` while any approval is pending.
- The requester cannot review their own request. A separate authorized user with `agent.approve` must approve or reject it.
- Approval expiry and immutable audit logging remain governed by the M2.4 controls.

### External LLM patient-data boundary

- `local`, `ollama`, `vllm`, `llama_cpp`, and `llamacpp` are treated as local providers. All other provider names are treated as external by default.
- Before an execution or a newly queued task is accepted, a conservative deterministic scan checks for patient-identifier indicators such as patient/MRN/national identifiers, email addresses, and Cambodian-format phone numbers.
- If a potential identifier is present and the configured agent uses an external provider, the request is rejected before it reaches a provider integration.
- No exception path currently authorizes PHI/PII transfer to an external LLM. A future exception requires a documented authorized data-processing arrangement, organization policy, data minimization/de-identification verification, and a gateway implementation approved through change control.

## Scope boundary

This package is a runtime policy gate, not a claim that all identifying data can be detected by regular expressions. It deliberately fails closed for the implemented indicators. The gateway invokes `evaluate_execution_safety` immediately before every provider call; M3 must provide the complete final prompt, including retries, tool results, conversation history, attachments, and supervisor-produced prompts.

## M3 integration contract

1. Preserve `waiting_approval` as a non-runnable state.
2. Never allow the supervisor, worker, queue, or retry mechanism to bypass pending approvals.
3. Send only the final, de-identified payload to an external provider after gateway policy approval; do not rely only on initial request validation.
4. Record policy decision metadata and provider destination in audit logs without storing the sensitive source payload in logs.
5. Treat unknown providers as external.
6. Keep clinical output visibly labeled as decision support and require qualified human review before operational use.

## Verification evidence

`test_m25_blocks_patient_identifiers_for_external_llms_and_gates_high_impact_work` verifies that:

- an external-provider request with a patient identifier is rejected;
- high-impact work is automatically held for approval;
- direct transition to running is blocked while approval is pending;
- self-review is rejected;
- a different authorized approver can release the work.

`test_m25_llm_gateway_and_tools` verifies mocked OpenAI, Anthropic, and Ollama adapter contracts, cost-based routing and fallback, gateway PII/approval enforcement, and tool permission, timeout, and output-limit enforcement.

Run the API tests from the repository root:

```powershell
docker compose up -d --build api
docker compose exec -T api python -m pytest -q tests
```

## M3 entry criteria

- M2.5 automated test suite passes.
- The external LLM gateway is designed to call this policy at the final egress boundary.
- Provider configuration has an explicit local/external classification.
- No M3 workflow can create autonomous diagnosis, prescription, referral, publication, deletion, payment, access change, or other high-impact outcome.
