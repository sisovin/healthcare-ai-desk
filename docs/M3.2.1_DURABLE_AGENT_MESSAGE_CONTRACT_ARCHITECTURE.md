# M3.2.1 — Durable Agent-to-Agent Message Contract

**Status:** Architecture and implementation package — ready for review before code or migration work.

## Purpose and boundary

M3.2.1 adds durable, organization-scoped agent messages to the existing conversation timeline. It is the contract foundation for M3.2.2 routing, M3.2.3 coordination, and M3.2.4 group-chat reads. It does not add a worker, delegation engine, direct agent-execution endpoint, or any approval authority.

M2.5 remains mandatory at runtime/provider boundaries. A message may report an approval request or decision, but it cannot create, approve, reject, expire, or bypass an `AgentExecutionApproval`.

## Verified starting point

Current MySQL head is `20261112_0011`. The existing schema already supplies:

| Existing capability | Source |
| --- | --- |
| Organization/conversation scoped, immutable sequence number | `conversation_messages` with `(organization_id, conversation_id, sequence_number)` uniqueness |
| Sender identity exclusivity | User/agent/system `CHECK` constraint and scoped agent foreign key |
| Per-conversation idempotency | `(organization_id, conversation_id, idempotency_key)` uniqueness |
| Correlation and causation fields | `conversation_messages.correlation_id`, `causation_id` |
| Atomic durable delivery source | `workflow_outbox_events` and transactional write path |
| At-least-once consumer deduplication | `workflow_event_consumptions` unique ledger |

The schema is not yet sufficient for the proposed agent-to-agent envelope because it lacks recipient identity/type, a first-class protocol message type set, and an immutable typed payload envelope. Its existing message-type `CHECK` also excludes `task_assigned`, `approval_requested`, and other M3.2 protocol events.

## Canonical envelope

The server produces this read/event envelope. Clients and agents do not provide authoritative values for `id`, organization, sender, recipient, sequence, correlation, or timestamp.

```json
{
  "id": "uuid",
  "organization_id": "uuid",
  "conversation_id": "uuid",
  "correlation_id": "uuid",
  "causation_id": "uuid|null",
  "sender_type": "agent",
  "sender_id": "agent-profile-uuid",
  "recipient_type": "agent|conversation|supervisor|system",
  "recipient_id": "agent-profile-uuid|null",
  "message_type": "task_assigned",
  "payload": {},
  "sequence_number": 1,
  "created_at": "2026-11-12T00:00:00Z"
}
```

`payload` is a protocol payload, not an unrestricted prompt/context store. It must contain only allow-listed, redacted metadata appropriate for the message type. Patient identifiers, secrets, raw tool output, raw provider errors, and hidden reasoning are prohibited. Full local encrypted content remains governed by the existing conversation-content policy.

## Contract and storage design

### Recommended additive table: `conversation_protocol_messages`

Do not overload `conversation_messages` for targeted delivery before its existing API contract is extended. Add a forward-only migration after `20261112_0011` with this table:

| Column | Rule |
| --- | --- |
| `id` | UUID primary key, server generated |
| `organization_id`, `conversation_id` | Required; composite FK to the scoped conversation |
| `sequence_number` | Required server-assigned timeline sequence; unique with organization/conversation |
| `sender_type`, `sender_agent_profile_id` | `sender_type='agent'`; required scoped FK to agent profile |
| `recipient_type`, `recipient_agent_profile_id` | `agent`, `conversation`, `supervisor`, or `system`; agent recipient requires a scoped agent ID, all broadcast/system forms require NULL |
| `message_type` | Enumerated protocol type |
| `payload_ciphertext` | Optional encrypted local payload |
| `payload_redacted` | Required redacted JSON/text view, size-limited and schema-validated |
| `data_classification`, `encryption_key_ref`, `retention_expires_at` | Same local data-protection posture as conversation messages |
| `idempotency_key`, `request_fingerprint` | Server-scoped retry/deduplication pair |
| `correlation_id`, `causation_id` | Required correlation; optional causal predecessor |
| `created_at` | Server timestamp |

Required constraints and indexes:

- Unique: `(organization_id, id)`.
- Unique: `(organization_id, conversation_id, sequence_number)`; sequence is shared with the visible timeline by allocating it under the locked conversation row.
- Unique: `(organization_id, conversation_id, idempotency_key)`.
- Composite FK: `(organization_id, conversation_id)` → `conversations`.
- Composite FK: `(organization_id, sender_agent_profile_id)` and, where non-null, `(organization_id, recipient_agent_profile_id)` → `agent_profiles`.
- `CHECK` rules for allowed sender/recipient forms and allowed protocol `message_type` values.
- Index: `(organization_id, conversation_id, created_at)` and targeted-recipient lookup index.

### Protocol message types

M3.2.1 supports only these server-created protocol types:

- `task_assigned`, `agent_progress`, `agent_result`, `task_failed`
- `approval_requested`, `approval_decided`
- `conversation_started`, `conversation_completed`, `conversation_cancelled`

`approval_requested` and `approval_decided` are projection/notification events whose authoritative source is the M2.5 approval record. Their payload contains only the approval/execution ID, status, and safe display metadata; the service checks the referenced record and organization scope before inserting either event.

## Server-owned authorization and ordering

1. External clients may submit only a bounded **intent** to an authorized API. They cannot submit a claimed `sender_id`, `organization_id`, `recipient_id`, or sequence number.
2. The coordinator resolves the organization from the authenticated access context, the conversation from the scoped route, and the sender agent from the assigned execution/task. It verifies active status, published version, project assignment, active conversation membership, and recipient membership/assignment.
3. The service locks the conversation row and allocates the next sequence across user-visible and protocol messages. The sequence and created timestamp are immutable.
4. It validates a typed payload allow-list, redacts/encrypts content, inserts the protocol message, audit record, and `workflow_outbox_events` event within **one MySQL transaction**, then commits once.
5. The outbox payload contains protocol message ID, event version, organization/conversation/correlation IDs, and safe routing metadata only. Consumers fetch the durable message by ID; they do not trust a rich delivery payload.
6. Repeated requests use server-calculated request fingerprints. Same idempotency key + same fingerprint returns the existing message; a differing fingerprint is a conflict.

## Safety invariants

- No message can call `review_execution_approval`, set approval status, or mark a waiting execution runnable.
- A coordinator may emit an approval notification only after reading the durable M2.5 approval decision in the same organization scope.
- Retries, Redis replay, fallback, delegation, and parallel routing create no alternate approval transition.
- Before an external LLM/provider invocation, the existing M2.5 gateway still re-evaluates the final prompt for PII and approval. Messaging never conveys an approval grant to that gateway.
- Outbox/audit metadata excludes raw patient content, credentials, and provider exception text.

## API compatibility

M3.2.1 is additive. Existing `/api/v1/conversations` user-message endpoints and response schemas remain unchanged. New internal service methods and later read APIs use protocol-message schemas; no existing client is required to understand protocol events.

## Schema Contract Revision 1 — review remediation

**Status:** Required corrections accepted for architecture review. No migration, worker, or API implementation is authorized by this revision alone.

### P0 — one durable timeline allocator

The per-table unique indexes proposed above do **not** establish a globally unique timeline across `conversation_messages` and `conversation_protocol_messages`. The current user-message path uses `MAX(conversation_messages.sequence_number) + 1`; it must be changed as part of M3.2.1 before protocol writes are enabled.

The forward-only migration design must add this server-owned column to `conversations`:

| Column | Proposed definition | Invariant |
| --- | --- | --- |
| `next_timeline_sequence` | `INTEGER NOT NULL`, default `1`, `CHECK (next_timeline_sequence >= 1)` | The next unallocated sequence for all timeline-message tables in one conversation |

Migration backfill rule, after the protocol table exists but before it contains rows:

```text
conversations.next_timeline_sequence =
  max(existing conversation_messages.sequence_number, 0) + 1
```

The allocator algorithm is mandatory for **every** user-message and protocol-message write path:

1. Start the caller-owned MySQL transaction.
2. Lock its scoped conversation using `SELECT ... FOR UPDATE`.
3. Read `next_timeline_sequence` as the allocated immutable sequence, then increment it by one in the same transaction.
4. Insert the user or protocol message with that allocated number, then insert the audit row and outbox event.
5. Commit once. Any validation, encryption, audit, outbox, or insert failure rolls back the counter increment with the message.

The existing unique constraints remain valuable as table-local corruption guards, but the locked durable counter is the cross-table invariant. No `MAX(sequence_number) + 1` query may remain in either write path after M3.2.1.

Required integration proof: concurrent user-message and protocol-message writes through separate MySQL sessions must produce a union of unique, gap-free committed sequence values. A protocol-to-protocol-only test is insufficient.

### P0 — authoritative sender and recipient routing

The protocol service accepts an **intent** with a message type and bounded payload. It does not accept an authoritative sender, recipient, organization, sequence, correlation, or causation value from a client.

For an agent-originated message, the server resolves and verifies all of the following in the same organization scope:

1. The conversation exists and belongs to the authenticated organization; its project is the routing project.
2. The sender `AgentProfile` is `active`.
3. The sender has an active `AgentProjectAssignment` to that conversation project.
4. The sender has a published `AgentVersion`; for task-bound messages, it must equal the version pinned on the referenced `ConversationTask`/`AgentExecution`.
5. The referenced task/execution belongs to the same organization and conversation and is assigned to that sender.
6. The recipient is one of `agent`, `supervisor`, or `conversation`:
   - `agent`: an active, project-assigned, published recipient with an active task assignment in the same conversation.
   - `supervisor`: server-resolved coordinator identity only; no client-supplied supervisor ID.
   - `conversation`: broadcast only to active conversation participants/read projection; no agent identity is implied.

M3.2.1 does not use a client-supplied privileged sender identity. It also does not infer authorization from an agent profile ID alone. A future coordinator may add agent `conversation_members` records, but task/execution binding is required until that lifecycle is implemented and tested.

### P0 — idempotency and duplicate-key races

The protocol table must have:

```text
UNIQUE (organization_id, conversation_id, idempotency_key)
```

The service computes `request_fingerprint` from canonical JSON of the validated payload plus immutable authoritative routing context:

```text
message_type, sender agent/task/execution identity, resolved recipient identity,
conversation ID, causation ID, and canonical allow-listed payload
```

On replay, same key and same fingerprint returns the original message. Same key and a different fingerprint returns a conflict. A concurrent duplicate-key `IntegrityError` must roll back the failed session and re-read the durable row; it then deterministically returns the existing message or conflict. It must not create a second audit/outbox record.

### P0 — approval notification rule

`approval_requested` and `approval_decided` are projections only. Before emitting either event, the service reads the referenced M2.5 `AgentExecutionApproval` and its execution inside the organization-scoped transaction.

- `approval_requested` requires an existing persisted `pending` approval.
- `approval_decided` requires an existing persisted terminal approval (`approved`, `rejected`, or `expired`) and its matching durable execution transition.
- No protocol message writes approval state, execution state, reviewer ID, or a runnable flag. A pending approval remains non-runnable regardless of retries, delegation, delivery duplication, or message content.

### P1 — payload allow-list and limits

All protocol payloads use canonical JSON, must be object values, and have a maximum **redacted serialized size of 16 KiB**. If local encryption is enabled, the encrypted representation has a maximum **64 KiB**. An oversize, non-object, unknown-field, or invalid-type payload is rejected before sequence allocation and before any outbox/audit insert.

| Message type | Allowed payload fields |
| --- | --- |
| `task_assigned` | `task_id`, `execution_id`, `task_type`, `agent_version_id`, `dependency_task_ids` |
| `agent_progress` | `task_id`, `execution_id`, `progress_percent`, `status`, `summary_redacted` |
| `agent_result` | `task_id`, `execution_id`, `result_reference`, `summary_redacted`, `status` |
| `task_failed` | `task_id`, `execution_id`, `error_code`, `summary_redacted`, `retryable` |
| `approval_requested` | `approval_id`, `execution_id`, `reason_code`, `expires_at` |
| `approval_decided` | `approval_id`, `execution_id`, `decision`, `decided_at` |
| `conversation_started` | `plan_id`, `strategy` |
| `conversation_completed` | `plan_id`, `status`, `summary_reference` |
| `conversation_cancelled` | `reason_code`, `cancelled_at` |

No payload schema permits patient identifiers, contact details, free-form provider prompts, credentials, raw tool output, raw exception messages, or hidden reasoning. `summary_redacted` is short server-redacted display text, not an arbitrary transcript.

### P1 — retention, encryption, and audit minimization

- Protocol payload ciphertext uses the existing conversation encryption mechanism and a validated key reference. Initial allowed key references are the configured conversation-key namespace; unknown or malformed references are rejected.
- Encryption failure fails the entire transaction. Plaintext fallback is prohibited.
- Key rotation is backward compatible: new writes use the active key reference; readers retain the ability to decrypt permitted historical key references until retention expiry. Rotation does not rewrite audit/outbox payloads with plaintext.
- Protocol payloads default to a configurable **90-day** retention expiry. On expiry, ciphertext is deleted or cryptographically rendered unreadable and the redacted display becomes a fixed retention marker; immutable audit records retain only action, IDs, timestamps, and safe status/reason codes required by policy.
- Outbox payload contains only protocol message ID, event version, organization/conversation/correlation IDs, recipient routing type/ID where needed, and idempotency key. Redis and audit metadata contain no raw patient content or credentials.

### Foreign-key and MySQL compatibility checklist

Before DDL is written, confirm against the current SQLAlchemy models and migrations `20261112_0009` through `20261112_0011`:

- Composite referenced columns are backed by a primary/unique index: `conversations (organization_id, id)` and `agent_profiles (organization_id, id)` already satisfy this requirement.
- New referencing/referenced `VARCHAR(36)` UUID columns use identical MySQL charset/collation and signedness/length definitions.
- The protocol table uses composite organization-scoped foreign keys rather than unscoped agent/conversation foreign keys.
- The `next_timeline_sequence` column type is compatible with existing `Integer` sequence fields; an overflow policy is documented before use.
