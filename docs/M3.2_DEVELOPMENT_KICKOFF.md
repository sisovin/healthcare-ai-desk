## Purpose

M3.2 builds durable, organization-scoped collaboration between the Supervisor and specialist agents. It adds Messenger-style group-chat protocol events, reliable routing through the existing transactional outbox and Redis Streams, and workflow coordination based on the M3.1 Supervisor, Agent Runtime, and M2.5 safety controls.

M3.2 is decision support. It does not authorize autonomous clinical action, patient-data egress to external LLMs, unrestricted tool execution, or an alternate approval mechanism.

## Non-negotiable operating rules

- M2.5 remains the sole safety and human-approval authority.
- Supervisor, agent messages, retries, delegation, parallel branches, provider fallback, dispatcher recovery, and Redis replay cannot approve or bypass high-impact work.
- External LLM egress continues to require PII protection and the existing final M2.5 gateway validation.
- MySQL remains the authoritative workflow database; Redis Streams are a recoverable delivery accelerator.
- Delivery is at-least-once. Every consumer side effect requires durable MySQL deduplication.
- All records, reads, and writes remain organization-, project-, conversation-, and agent-scoped.
- Existing APIs and Alembic history remain compatible. Migrations are forward-only; MySQL and Redis volumes must never be reset, dropped, recreated, or flushed.

## Architecture baseline

```text
Conversation API / Group Chat
  └─ RBAC, tenant isolation, server-owned ordering
       └─ Supervisor + Workflow Coordinator
            └─ MySQL authoritative state
                 ├─ conversations / messages / tasks / audits
                 ├─ protocol messages (M3.2.1)
                 └─ workflow outbox + consumption ledger
            └─ Redis Streams delivery accelerator
                 └─ XADD / XREADGROUP / XAUTOCLAIM / XACK
                      └─ Agent Runtime + M2.5 safety gateway
```

## M3.2.1 first implementation scope

M3.2.1 begins with the durable agent-to-agent protocol message contract defined in [M3.2.1 Durable Agent Message Contract Architecture](M3.2.1_DURABLE_AGENT_MESSAGE_CONTRACT_ARCHITECTURE.md).

Initial protocol types:

- `task_assigned`, `agent_progress`, `agent_result`, `task_failed`
- `approval_requested`, `approval_decided`
- `conversation_started`, `conversation_completed`, `conversation_cancelled`

The server, never the client, resolves sender identity, organization, recipient authorization, timeline sequence, correlation, causation, timestamps, and idempotency fingerprint. Protocol messages may report approval state but cannot mutate `AgentExecutionApproval` or execution authorization.

## M3.2.1 implementation gate

Before writing code:

1. Verify `alembic current` and `alembic check`; generate a migration only from the live head.
2. Approve the message envelope, recipient model, payload allow-list, retention, and size limits.
3. Confirm how user and protocol messages share a single server-owned timeline sequence.
4. Confirm no M3.2 worker is enabled before transactional persistence and authorization tests pass.

Definition of done:

- Protocol message, audit record, and outbox event commit or roll back as one transaction.
- Server-owned immutable sequence and idempotency behavior are tested under concurrency.
- Cross-tenant, cross-project, unassigned, inactive, unpublished, and unauthorized sender/recipient paths are denied.
- Duplicate delivery creates no duplicate side effect.
- Pending M2.5 approval remains non-runnable through every messaging/retry/delegation path.
- PII is protected locally and excluded from external egress plus outbox/audit metadata.
- Targeted integration tests and full regression have actual recorded results.

## Evidence and acceptance discipline

- Do not mark a package passed based only on implementation or documentation.
- Record exact commands, outputs, migration state, and the specific database/Redis behavior verified.
- Use UUID-scoped test records and disposable Redis streams.
- Do not use `FLUSH*`, volume reset, destructive environment rebuild, or edits to historical migrations.
- Local acceptance is not production certification. Deployment/restart runbooks, monitoring, capacity, and production configuration need a separate authorized acceptance exercise.
